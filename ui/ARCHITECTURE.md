# `ui/` — architecture

The front end: a TypeScript application, built with Vite and React, that the `ragondin ui` subcommand serves (ADR-C36). It is **not a crate** and sits outside Cargo, but it is **load-bearing** in the sense `AGENTS.md` § Documentation ships with the code it describes means: this file is read before `ui/` is modified, and a diff that falsifies it corrects it in the same pull request (ADR-C36 § 5).

Today it is the governed application, its design system under `design/` (§ The design system), and the shell every screen mounts into: the API client over types generated from the API's description (§ The client, § The generated types), the router and the URL state of the six screens (§ The router and the URL state), the top bar with the workspace, the theme and the connection state (§ The shell), and the build identity handshake (§ The build identity handshake). The Runs, Pipeline, Compare, Replay, Editor and Setup screens are built (§ The Runs screen, § The Pipeline screen, § The Compare screen, § The Replay screen, § The editor, § The Setup screen). Beside the shell is the pipeline canvas, in read mode and in write mode (§ The canvas), the component Replay, the editor and Compare draw graphs with.

## The gates

`npm run check` is the one command, and CI's `ui` job and a contributor run it; `just check-ui` runs its steps, the build first (below). It runs, cheapest first:

| Script | What it does |
|---|---|
| `types:check` | Fails when `src/api/types.ts` is not what the API's description generates (§ The generated types). |
| `lint` | ESLint over everything, warnings are errors. |
| `typecheck` | `tsc -b` over the application and the tooling, both strict. |
| `test` | Vitest: component tests in a DOM, governance tests in Node. |
| `build` | `vite build` into `dist/`, the third-party notices included (§ The third-party notices). |
| `notices` | Re-reads `dist/third-party-notices.txt` and fails when a runtime package's or a font licence's notice is absent or stale. |
| `audit` | The font licence audit, the npm licence audit, then the advisory audit (§ The dependency audit). |

`just check-ui` runs `npm ci` first, so the gate always installs exactly the lockfile. The install and the build are `just build-ui`'s, which `check-ui` depends on; `check-ui` then runs every other step of `npm run check`, as `scripts/check-steps.mjs` prints them: read from `package.json` rather than named, and a failure, rather than a second build, if that script stops naming `npm run build` as a step. `tests/check-steps.test.ts` tests both cases. `just check` runs `build-ui` before the feature-gated Rust tests, which embed `dist/`, so they never embed one left by an older checkout, and the build runs once per `just check`. **The Rust build does not need Node** (ADR-C36 § 5): no cargo command and no cargo-based `just` recipe runs anything under `ui/`. The one thing cargo reads there is `dist/`, the build's output: `bin/ragondin`'s build script embeds it under the `ui` feature when it exists, and a page saying the UI was not built when it does not (`bin/ragondin/ARCHITECTURE.md` § The ui subcommand). Only `just check`, which covers both worlds, and the recipes of this tree — `build-ui`, `check-ui`, `gen-ui-types`, `test-ui-e2e`, `ui-dev-fixture` — run Node.

**The end-to-end journeys are not a step of `npm run check`**: they need the binary built with `ui,bm25,onnx` and the fixture workspace, which only cargo makes. `just test-ui-e2e` runs them, and `just check` runs it after `check-ui`; CI runs the same steps at the end of its `ui` job (§ The end-to-end journeys).

## The one-address rule

The UI talks to one address: the origin that served it. Every request goes to the binary's JSON API under a **relative** base address, `API_BASE` in `src/api/base.ts`, through the one client in `src/api/client.ts` and the one event stream wrapper in `src/api/events.ts`, and every asset — fonts included — is bundled and served by the binary, never fetched from a CDN or any other host (ADR-C36 § 5, applying ADR-012 on the browser side). `src/api/base.test.ts` asserts that the base address resolves against whatever origin served the page.

`ui/` is the **only consumer of `/api/v1`** (ADR-C36 § 2). That is what keeps the API internal rather than a stable boundary: it changes with the UI, in the same pull request. A second consumer is a decision, not a change.

## The network lint

The second, best-effort layer of that rule. `eslint.config.js` makes it an error, anywhere outside `src/api/`, to name the browser's network primitives — `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource` — whether as a bare global (`no-restricted-globals`) or as a property of `window`, `globalThis`, `self`, `top`, `parent`, `frames` or `opener`, dotted or with a literal key (`no-restricted-properties`). Each message names `src/api/` and this section. It covers every source extension `tsc` and Vite accept — `.js`, `.mjs`, `.cjs`, `.jsx`, `.ts`, `.mts`, `.cts`, `.tsx` — because a file the lint does not match is a file it silently does not read. `tests/network-lint.test.ts` lints the same code as if it lived outside and inside `src/api/`, against the real configuration, and once per extension.

The shell's own network access passes it with no exception added: every `fetch` is in `src/api/client.ts`, every `EventSource` in `src/api/events.ts`, and the tests' doubles of both in `src/api/testing.ts`, which a test anywhere imports so that it names no primitive itself.

It is a **scan of source text, and it does not see**:

- a property computed at run time (`window['fe' + 'tch']`), or one reached through an alias or a longer path: `const g = globalThis; g.fetch(...)`, `window.window.fetch`, `document.defaultView.fetch`, `Reflect.get(window, 'fetch')`;
- a worker (`new Worker(url)`), whose own code the lint reads only if it is a source file here, and whose script address is not checked;
- a primitive named by a dependency's own code, which the lint never reads;
- other ways to reach the network: an `<img>` or `<link>` pointing elsewhere, a `navigator.sendBeacon`, a dynamic `import()` of a URL.

A green lint is evidence, not proof. **The layer that holds is the content security policy the binary sends** (ADR-C36 § 1 and § 5), whose default source is `'self'`: the browser itself refuses any other origin, for the UI's code and for every dependency it bundles.

## The dependency audit

`deny.toml` transposed, since the two toolchains cannot share a file. The policy is `scripts/audit-policy.mjs`.

**Licences** (`scripts/check-licenses.mjs`, logic in `scripts/licenses.mjs`). Every package in the lockfile, runtime and development alike, must carry a licence expression satisfiable from `LICENSE_ALLOW`. That list is a **copy of `deny.toml`'s `[licenses] allow`**, duplicated on purpose and kept identical by `tests/licenses.test.ts`, which reads both. An installed package is read from its own `package.json`; a platform-specific package this machine did not install is read from the licence the lockfile records, so every platform's tree is audited, as `deny.toml` audits every target. A missing licence field, a `WITH` exception, `UNLICENSED` or `SEE LICENSE IN …` fails.

**There is one policy and no per-package licence exception.** A licence outside the list is refused whatever the package's role, runtime or development. A dependency that needs another licence is admitted by adding that licence to `deny.toml`, for the reasons its comments give, and to the copy in the same change — as `BlueOak-1.0.0` was, for `minimatch`, which ESLint depends on unconditionally.

**Fonts** (`scripts/check-font-licenses.mjs`, logic in `scripts/font-licenses.mjs`). A font is a committed file, not a package, so no lockfile names it and the npm audit above never sees it. This check holds it to the same list. It walks all of `ui/` but `node_modules/` and `dist/` for font files, and every one must sit directly in `design/fonts/` with exactly one row in `design/fonts/LICENSES.md`, which is the manifest. The row names its licence, which must be on `LICENSE_ALLOW`; its licence text, which must sit in the same directory, named without a path, and be pinned by its own SHA-256; and the SHA-256 the font had when it was committed. A font or licence text edited after the fact fails, a row listed twice fails, and a row whose file is gone fails. It reads files only, so it needs no network. `OFL-1.1` entered `deny.toml` and its copy for the design system's typefaces, as the comment there says.

**Advisories** (`scripts/check-advisories.mjs`, logic in `scripts/advisories.mjs`). Runs `npm audit --audit-level=high --json` and fails on any high or critical advisory that `ADVISORY_EXCEPTIONS` does not name. npm has no ignore list, which is why the report is read rather than npm's exit code trusted; a missing or unrecognised report fails. Every exception carries:

| Field | Content |
|---|---|
| `id` | the advisory's GHSA identifier |
| `date` | the day it was added, `YYYY-MM-DD` |
| `reason` | why it is an allowance rather than a fix |
| `removedBy` | the issue that removes it, as `#<number>` |

— the shape `deny.toml`'s `ignore` comment prescribes. An exception that no longer matches anything is reported, so it gets deleted. The list is empty today. The advisory audit reads the registry's advisory database, which changes daily: like `just check-deny`, it can go red on a branch whose diff caused nothing.

Adding a dependency is governed by `DEPENDENCIES.md`, whose rule is `AGENTS.md` § Conventions'.

## The third-party notices

The binary embeds `dist/` and redistributes it, and MIT, ISC and BSD-3-Clause each require the copyright and permission notice to accompany a copy. So the build writes `dist/third-party-notices.txt`, which the binary serves at `/third-party-notices.txt` (§ How the assets reach the binary). The logic is `scripts/notices.mjs`, a Vite plugin registered in `vite.config.ts`, read from the installed tree as the licence audit is rather than by a generator package, for the reason the audit gives: it has to be read to be trusted.

**What it lists.** One block per package — name, version, the licence field of its `package.json`, and the text of its own licence file: `LICENSE`, `LICENCE` or `COPYING`, any case, bare or with a `.` or `-` suffix (`LICENSE.md`, `LICENSE-MIT`, `LICENSE.APACHE2`) — then one per font licence text in `design/fonts/LICENSES.md`, with the font files it covers. The packages are:

- **every runtime package of the lockfile**: each entry not marked `dev` or `devOptional`, which is the whole closure `dependencies` can bundle. It is a superset of what the bundle holds — the canvas library's tree is listed before a screen imports it, and `@types/*` packages carry no code — and a superset errs on the side the licences require;
- **Vite**, a development package, because the build writes Vite's own code into the bundle: the modulepreload polyfill and the CommonJS helpers (from `@rollup/plugin-commonjs`, whose notice Vite's `LICENSE.md` carries). `VIRTUAL` in `scripts/notices.mjs` maps each such virtual module to its package.

**What fails the build.** A listed package that is not installed or ships no licence file. And a module of the build's graph that comes from neither `ui/`'s own code nor a listed package — a development package imported by application code, a file outside `ui/`, or a virtual module `VIRTUAL` does not name — so a package that reaches the bundle as a module cannot ship without a notice. An optional package this machine did not install is skipped, since the build cannot have bundled it.

**What the graph check does not see.** It reads the build's module graph, and two things reach the bundle without being modules of it: an asset reached through a CSS `url()` — a font or an image a stylesheet names, which is emitted as a file and never enters the graph — and the glue code Rollup and esbuild write around modules (chunk wrappers, interop and JSX-runtime shims of their own). Today every `url()` names a font under `design/fonts/`, whose licences the font blocks cover, and the glue is the tools' own output, not a package's code. A stylesheet that names an asset from a package needs that package listed by hand.

**A package that ships no licence file.** The build refuses it, by design: a notice is the package's own text, never a guess. When a package that has to be bundled ships none, the remedy is an explicit, reviewed override: a map in `scripts/notices.mjs` from `package@version` to a text file committed under `ui/` holding the licence text, with the reason it is needed (where the text was taken from, and why the package ships none). An entry is keyed to one version, so an upgrade drops it and the build asks again; it is added only when a real package needs it, in the pull request that adds that package, and named there under its own heading. No such map exists today, because no package needs one.

**The Rust crates.** The crates linked into the binary carry notice obligations of their own. The binary ships them itself: it serves them at `/third-party-notices-rust.txt` and prints them with `ragondin --notices` (`bin/ragondin/ARCHITECTURE.md` § The licence notices of the Rust crates). This file's header points there.

**What re-checks it.** `npm run notices`, after the build, re-reads the written file and fails when the block of a runtime package or a font licence — name, version, licence and text, exactly as written — is absent, so a file edited or left stale fails. `tests/notices.test.ts` tests each rule over throwaway lockfiles, runs the real production build into a temporary directory and checks what it wrote, and fails if `npm run check` stops running the re-check after the build. In `bin/ragondin`, the release assertion fails a shipped binary that does not serve the file (`bin/ragondin/ARCHITECTURE.md` § The assets and the notice page).

The font notices repeat what `design/fonts/` already ships beside the fonts, because the binary serves the font files and not that directory.

## The generated types

`src/api/types.ts` is **generated from the API's golden description**, `runtime/ragondin-api/api/v1.json`, and never written by hand (ADR-C36 § 2). `just gen-ui-types` regenerates it; it is committed so a change to the API reads as a diff of the types in the same review. It holds one `export type` per schema of the description, each with the description's own documentation; `Paths`: for every path and method, its path parameters (`params`), its query parameters (`query`) and request headers (`headers`) when it declares any — each optional unless the description marks it `required`, with the description's documentation — its request body and its success response; and `EMPTY_ANSWERS`, the operations whose success response has no body, which the client reads (§ The client). The client's signatures are derived from `Paths`, so a screen cannot ask a path the description does not have or read a body as the wrong type.

**The freshness check** is `scripts/check-api-types.mjs`, the `types:check` step of `npm run check`: it regenerates into a temporary file and compares it with the committed one, so a description changed without `just gen-ui-types`, or a hand edit of `types.ts`, fails the gate with the first differing line and the recipe to run. `tests/api-types.test.ts` runs it on a fixture — current, a changed description, a hand edit — and asserts that `npm run check` runs it.

**The generator is a script here, `scripts/api-types.mjs`, not a package.** Every OpenAPI-to-TypeScript generator on npm that was evaluated reads YAML through `js-yaml`, which depends on `argparse`, licensed Python-2.0 — off the allow list both toolchains share (§ The dependency audit) — and `openapi-typescript`, the usual choice, also declares a peer dependency on TypeScript 5, which this tree is past. Admitting one would be a change to `deny.toml`'s policy for a development convenience. The description is small and uses a fixed set of schema forms — objects, `required`, maps through `additionalProperties`, arrays, `$ref`, `enum`, `oneOf`, `anyOf`, `allOf`, `nullable` — so the script renders exactly those — and reads `additionalProperties: false` beside `properties`, which a request body that refuses an unknown field states, as absent, since a TypeScript object type is closed to literals already and the type does not change — and **throws on any other**, naming where: a change to the description's shape stops generation rather than degrading a type to `unknown` or dropping a constraint silently, and is then raised against `runtime/ragondin-api`, never patched in `types.ts`. What it refuses, each with a test: an unknown schema keyword; an object with neither `properties` nor `additionalProperties`, or with both; `properties`, `required` or `additionalProperties` on a type that is not `object`; a `required` name that is not a property; a `$ref` outside the description's schemas or to a schema it does not define; a schema name that is not a TypeScript identifier, or one of the names the file exports itself; an OpenAPI version other than 3.0.x; a path-level key other than a method (path-level `parameters` or `summary` included); an operation, parameter or request-body keyword it does not check (`security`, `deprecated`, …); an optional request body; a parameter in a cookie or in any location but the path, the query string and a header, naming the operation; a parameter name declared twice in one location — for a header, in any case, since HTTP reads `If-Match` and `if-match` as one; no success response, or more than one; a success body that is not JSON — but for an event stream, a success body of `text/event-stream` alone, which `EventSource` reads and the client never does: its `response` is `never`, it is not an empty answer, and its events are typed by the schema it names, rendered as every schema is (`GET /jobs/events` and `JobEvent`) — that schema must be present, and is refused on the same grounds as any other. String literals and non-identifier property names are written with JSON's escaping, which is TypeScript's.

## The client

`src/api/client.ts` is the one client over the API: `get`, `post`, `put`, `patch` and `del` on the relative base address, typed by `Paths`. After the path (and a write's body) come the path parameters, when the path has any, then the options, `{ query, headers, signal }`: the query and the headers when the operation declares either, typed by the operation's `query` and `headers` and required only when one of them is, and on every operation an optional `AbortSignal`, the caller's own and never sent, which is passed to `fetch` so a view can cancel a request a newer one supersedes. **The query string is serialized here, by `URLSearchParams`**: every reserved character percent-encoded, a space as `+`, an absent parameter left out, and no `?` when none is left. **A declared header is set here** too, only when given. So no screen writes a query string or a request header by hand, and none can send a parameter or header the description does not declare for that operation. **Every outcome is a value**, `{ ok: true, value }` or `{ ok: false, problem }`, never an exception a caller could forget to catch, so a result whose failure goes unhandled is visible at the call site (the front-end design, § 8).

A failure is an `ApiProblem`: `code`, `message`, `hint`, `location` (a validation failure's node or edge, else null), `status` (null when no answer arrived), `name`, the parameter a `parameter_invalid` names, and `link`, where a `run_exists` says the run id is held (`/api/v1/runs/<id>` or `/api/v1/jobs/<id>`), each present only when the problem body carries it. An `application/problem+json` answer is read into one as the API sent it, its `code` one of the description's enum. A problem body is shape-checked — an object with a string `code`, `detail` and `hint`, and a `location` that is absent, null, or an object carrying both of its required members — a node (a string or null) and an edge (null, or its two ends and its port) — before it is believed, so the error state never renders a location that is not one. Five failures never reach the API's error handling, and the client names them itself:

- `network_failed`: no answer — the server is down or unreachable — or an answer whose body broke off while being read;
- `response_unreadable`: an error status without a problem body; a problem body that is not JSON or fails the shape check; a success body that is not JSON; or an empty success body, a 204 included, from an operation that declares a body — only an operation listed in `EMPTY_ANSWERS` may answer empty, or a `null` would stand in for a type it is not. Each means the two sides disagree on the API;
- `build_mismatch` (§ The build identity handshake);
- `request_invalid`: a request refused before it is sent, because a path parameter is `.` or `..`, which encoding leaves as it is and a URL resolves as another path;
- `request_aborted`: a request whose signal aborted, before its answer or while its body was read — told apart from `network_failed` by the signal, not by the error's name. **It is never rendered**: only the view that asked can cancel, it cancels a request it has already superseded, and every reader that passes a signal drops the outcome of a request whose signal aborted.

Each message names the request, `GET /api/v1/workspace`, so the inline error says what failed. **Nothing in the client throws**: reading the body is inside the same guard as the request.

**The build identity travels with its answer**: every `ApiResult` carries `build`, the `x-ragondin-build` header of the answer it came from, problems included, or null when no answer arrived or it carried none. It is not state on the client, so two requests in flight never report each other's identity. The description declares request headers only, never a response's, so that one name, `BUILD_HEADER`, is written in `client.ts` rather than generated.

Tests mock the network at the request level: `src/api/testing.ts`'s `mockApi` replaces `fetch` with answers keyed by the description's own method and path template — `'GET /workspace'`, `'POST /compare'` — and typed by the generated body, so a mock of a path the API does not have, or a body of the wrong shape, does not compile. A template matches the whole path, which a query string may follow, and the request is recorded with its query string, so a test asserts the parameters a screen sent (`GET /api/v1/runs/<id>/queries?missing_gold_at=10`). The mock answers whatever query string comes, an unexpected one included, so only an assertion on `requests` catches a stray parameter. A `GET` may answer from the query string and the path it was sent — one template answering two runs' ids — a `POST` or a `PUT` from the request body it was sent, typed as its path's, and a `PATCH` from that body and the path, while a `DELETE` is mocked like a `GET` without a function; the mock returns each request's parsed body beside it, so a test asserts what a screen sent, and each request's `signal` beside it; a request whose signal aborts before its answer is rejected with an `AbortError`, as `fetch` rejects one, so a test asserts that a screen cancelled what it superseded. No server is started in a unit test. **The doubles never reach the bundle**: an ESLint `no-restricted-imports` rule refuses an import of `src/api/testing.ts` from anything but a test — through a path naming `api/testing` from anywhere, and as a sibling or parent (`./testing`, `../testing`) from inside `src/api/` — and `tests/test-doubles.test.ts` checks the rule and reads the production build for the doubles' strings.

## The router and the URL state

`src/routes.ts` is the URL state contract: the `Route` union names each screen and the state it carries, `formatHash` writes it and `parseHash` reads it back, `useRoute` follows the hash, and `navigate` moves to a route — as a new history entry, or with `{ replace: true }` in place of the current one, so Back skips it (for a correction, such as a default filled in, or for state within one view, such as Runs' selection — never for a move to another view). The addresses are the design's (§ 3), so a link pasted into an issue reproduces the view:

| Hash | Screen and state |
|---|---|
| `#runs` (or empty), `#runs?sel=<id>,<id>…` | Runs, and the runs selected for Compare in the order they were checked |
| `#runs/job/<id>`, `#runs/job/<id>?sel=…` | Runs, showing one job of the queue — where a toast's Open and `run_exists`'s Open land — with the selection beside it |
| `#runs?launch=<pipeline>&up_to=<node>`, `#runs?launch=<pipeline>`, `…&benchmark=<name>`, `…&benchmark=<a>&benchmark=<b>…` | Runs with the launch panel open on that pipeline, cut at that node — where the editor's "Run up to this node" lands — or whole; on that benchmark — where the Pipeline screen's Run lands — or on several, the key repeated with one value each, in order, a name repeated kept at its first place only — where "Launch the N missing runs" lands; beside a selection or a job. `up_to` or `benchmark` without `launch` is no route |
| `#runs?bench=<key>`, `…&bench=<a>&bench=<b>…` | Runs with the benchmark filter: the benchmarks whose rows are shown, each by its row model key, beside a selection, a job or a launch panel |
| `#pipeline`, `#pipeline/<name>` | Pipeline, before a pipeline is chosen and with one |
| `#compare`, `#compare/<id>+<id>…?baseline=<id>` | Compare: the runs, joined by `+`, and the baseline — each by its 12-character prefix where that names one run of the listing (`addressIds` in `src/runs/model.ts`), else in full |
| `#replay`, `#replay/<run>`, `#replay/<run>/q/<query>?with=<run>`, `#replay/<run>/q/<query>/node/<id>?with=<run>`, `…?with=<run>&set=regressions&metric=<name>` | Replay: before a run is chosen; one run, before a query is chosen; one query of one run, optionally beside another run (`with`); the node selected on it; and a set of queries kept to step through — the run's regressions against the run beside on that metric, where Compare's "Replay the N regressions" lands. `set` and `metric` come together and need `with`; `set` takes no other value |
| `#replay/job/<id>`, `#replay/job/<id>/q/<query>`, `#replay/job/<id>/q/<query>/node/<id>` | Replay over a failed or cancelled run job's partial traces, alone: before a query is chosen; one query; and the node selected on it. A run is named by its hash, so `job` is never one |
| `#editor`, `#editor/<name>`, `#editor/<name>/node/<id>` | Editor: before a pipeline is opened; one pipeline; one pipeline and the node selected on it |
| `#setup`, `#setup/benchmarks`, `#setup/services` | Setup, at the top or scrolled to one section, which takes focus |

Every value is percent-encoded, so an id holding `+`, `,` or `/` round-trips. An address that names no screen, or names one malformed — a missing segment, `?baseline=` without runs, an empty `baseline`, `with` or `sel` value, a value of `.` or `..` (typed, or escaped as `%2E%2E`), a broken escape — is **no route**, and the shell says so and offers Runs, rather than guessing a screen. The job Runs shows, and the launch panel it opens, are state within Runs, as a selection is: `viewOf` is `#runs` with or without them, and the screen moves focus to the job itself (§ The Runs screen). Setup's section is a place on one page, not another view: `viewOf` is `#setup` whichever section the address names, so a move between sections focuses that section (§ The Setup screen) and the shell leaves its heading alone. A screen reads its state from the `Route` it is given and never parses the hash itself; a screen that needs more state extends its variant here, in its own issue.

**Hash routing**, as the design writes the addresses: a hash never reaches the server, so every deep link works whatever serves the page and from whatever context it is pasted. **The router is this module, with no dependency.** ADR-C36 § 5 asks for a typed client-side router; the two requirements are typed state and hash routing, and none of the candidates met both within the licence policy: TanStack Router depends on `isbot`, licensed Unlicense, and wouter is Unlicense itself, both off the allow list; React Router types a route's parameters only in its framework mode, through a build plugin that generates them, and in library mode hands a screen strings, so the typed contract above would still be written here and the package would add only the matching; `type-route`, typed and hash-capable, has not been released since 2023, and its hash mode writes its own `/#/…` address back as a path, giving `#/#/runs`. What the module has to do — six shapes, parse, format, follow `hashchange` — is short and tested per route. Taking a router package later is a runtime dependency named under its own heading; it would replace this module, never sit beside it.

## The build identity handshake

The UI and the API it talks to must be the same build (ADR-C36 § 1). **The UI's side of the identity comes from the build**, never from a response, or the comparison would prove nothing: `vite.config.ts` defines `__RAGONDIN_BUILD__` from `scripts/build-identity.mjs`, and `src/shell/build.ts` exports it as `BUILD`. That script computes the identity **from the source the binary reads its own from, by the rule it reads its own by**: `<version>+<commit>[-dirty]`, the `ragondin` crate's version — `[workspace.package]`'s, which it inherits, or its own if it declares one — then the commit and whether the tree differs from it, or `<version>+unknown` outside a checkout. **The git half of that rule is one file, `bin/ragondin/build-identity.rule`**, which the binary's build script reads too (`bin/ragondin/ARCHITECTURE.md` says how): the commit is `git rev-parse --short=12 HEAD`, and the tree is dirty when `git --no-optional-locks status --porcelain --untracked-files=no` prints anything — a tracked file modified or a change staged. **An untracked file, a Finder `.DS_Store` say, leaves both identities clean**, and **a tracked change marks both `-dirty`**: when only the binary applied a dirty rule, and counted untracked files in it, any such file made the two differ and the page refused to load. `tests/build-identity.test.ts` pins the rule on fixture checkouts, as the binary's own tests do. Both sides read the same files of the same commit by the same rule, so a UI built with the binary it is embedded in carries the identity that binary reports; a commit moves with a change to either side, which a version alone would not. Changing the rule is changing that file, and both builds follow.

The shell compares on load, when `GET /workspace` answers, and again whenever the event stream reconnects (§ The connection state), since the server may have been restarted as another build meanwhile. `judgeBuild` decides:

- **the same build**: the page continues, and forgets any earlier reload;
- **another build, for the first time**: the page reloads once, which fetches that build's own UI, and remembers in `sessionStorage` which identity it reloaded for;
- **the same other build after that reload**: the page refuses, with the error state naming both identities (`build_mismatch`) and how to resolve it — never reloading forever;
- **an answer without an identity** counts as another build; a request that got **no answer** carries nothing to compare and is shown as the network failure it is.

When `sessionStorage` is unavailable the tab cannot remember having reloaded, so it refuses at once rather than risk a reload loop.

## The connection state

`src/api/events.ts`'s `openEvents` wraps `EventSource` on the relative base address. The browser retries a dropped stream by itself while it can; when it gives up — the source is closed, as after an error status — the wrapper opens a new one, one second later, doubling up to ten seconds, and never stops. It reports `connecting`, `connected` or `disconnected`, which the top bar shows as the words `connecting`, `connected` or `disconnected — retrying` beside a filled dot or a hollow ring: **the state never reads as current while the stream is down** (the front-end design, § 8). Every connection after the first calls back so the shell re-checks the build identity; the first is not re-checked, because the page load just did.

A stream's named events — the SSE `event` field — reach `events.on` with their name, for the names listed in `events.names`, as `EventSource` dispatches them; `onMessage` receives only unnamed ones. `restart()` drops the connection and opens a new one after the retry delay; a new `EventSource` sends no `Last-Event-ID`, so the server begins it afresh.

The shell opens the job queue's stream when it is told to follow it (`followJobs`), as `src/main.tsx` tells it, and the top bar shows that stream's state (§ The job stream); without it, no stream is opened and the bar shows none. The wrapper is tested against a fake stream, `FakeEventSource` in `src/api/testing.ts`, which a test drives by hand, named events included.

## The job stream

`src/api/jobs.ts` reads `GET /jobs/events` for every screen that follows the job queue — Setup's downloads (§ The Setup screen), Runs' jobs and the launch flow (§ The Runs screen), the toasts. `openJobStream({ onEvent, onState, onReconnect })` opens it through `openEvents` (§ The connection state), listening for every event name the generated `JobEvent` gives — listed once, as a record over the union, so a name added to the description does not compile until it is listed here — and hands each event on as a `JobEvent`, its data parsed and shape-checked: a listing's jobs; a job's id; a state and a work of a kind the description gives — each kind checked by a record over the generated union, so a new kind does not compile until it is — with a running job's counts numbers (its total a number or null), a failure's error and a work's benchmark strings, a failed or cancelled job's count of the traces it kept a number, and a job's faults a list whose every entry has a string reason. A screen that follows the stream passes `onState`, and says while it is `disconnected` that what it shows of the queue is the last known (the front-end design, § 8), and `onReconnect`, which re-checks the build identity as the shell does for its own stream (§ The build identity handshake). `applyJobEvent(jobs, event)` is the queue a screen holds, by id in the queue's order: `resync` replaces it with the listing; any other event sets its job, in its place when known, last when new — `fault` among them, which carries the job with every fault the queue reported beside it, the new one last; the map given is never changed. **A consumer that decides by an event's name decides by a record over the generated union too** — Runs' `SAYS_ORDER`, which events say the queue's order — so a name added to the description does not compile until each such consumer has said what it means for it.

**Faults beside a job** (`runtime/ragondin-api/ARCHITECTURE.md` § Faults beside a job): what went wrong without stopping the job — a layout not copied at launch, latencies left out of the median — each a reason and a time, on the job itself, published as a `fault` event as it is reported and persisted with the job, so a reload or a restart shows them again. Nothing is read again for one: the event carries the job. Each is said at the level a fault deserves, which is never an alert's, since the job goes on: a count on the job's row (§ The Runs screen), every reason in the job's view as a warning, polite, and a mention in the toast at the job's end, whose tone and lifetime are the outcome's. The fault itself raises no toast.

**Resuming after a drop.** The server numbers every event; a client that reconnects with `Last-Event-ID` is sent every event it missed, and in every other case the stream begins with `resync`, the whole queue (`runtime/ragondin-api/ARCHITECTURE.md` § The event stream). The reader keeps no bookkeeping of its own for this, because `EventSource` already does the half a browser can: its own retry of a dropped stream sends the last id it saw, and the server replays the gap; a stream the wrapper opens anew, once the browser gave up, is a new `EventSource`, which sends none and begins with `resync` — `EventSource` cannot set a request header, and the API reads the id from the header only. Either way `applyJobEvent` lands on the server's queue, and no screen acts across a gap. **An event that does not read is never handed on** — an unknown kind included, so no screen meets a state it cannot draw: the reader restarts the stream, so the next connection begins with `resync`, rather than hold a queue with one event silently missing.

**One stream per page.** `src/jobs/queue.tsx`'s `JobQueueProvider`, which the shell mounts, opens the one subscription through `openJobStream` and holds the queue `applyJobEvent` gives; `useJobs()` reads the jobs and the connection, re-rendering on each change, and `useJobEvents(listener)` hands a consumer each event with the queue before and after it. The queue is made once with the provider, so every consumer subscribes to the one object from its first render, and `useJobEvents` subscribes in a layout effect, during the commit: an event that arrives between a consumer's commit and its passive effects — a screen mounted while the stream is open — still reaches it. No screen opens a stream of its own, so the top bar, Runs, Setup and the toasts never disagree about the queue or about whether it is current, and moving between screens neither drops nor re-reads it. Without the provider — a screen rendered alone in a test — the queue is empty and the connection null, and nothing is opened. What a screen says while the stream is down is one wording, `src/jobs/stream.ts`'s: "Job stream disconnected, retrying.", or, while a job is under way, "Job stream disconnected, retrying: progress shown is the last known."

**The outcomes as toasts** (`src/jobs/Toasts.tsx`, mounted by the shell beside the screens): a run job's terminal transition the page saw — an event, or a `resync` after a drop that finds it ended — from a state not ended: "Run done · <pipeline> on <benchmark>", whose Open lands on the run filed (`id_mismatch`'s decided id when there is one) in Replay; "Run failed at <node>", whose Open lands on the job (`#runs/job/<id>`); "Run cancelled", with no action; each says ", with 1 fault" (or the count) after the outcome when the job carries faults as it ends — a fault reported at submission can follow a run that fails at once (`runtime/ragondin-api/ARCHITECTURE.md` § Known limits), and is then on the row and in the view only — said, never raised: a done run with faults is still a status that leaves on its own. Once per job, whatever replays — a toast is raised only on the transition from a state not ended, which a job makes once — and nothing for a job that had ended when the page opened, or for a download. A failure is design/'s critical toast — an alert — and `persist`s until acted on (the front-end design, § 8); the others are a status, polite, and leave after six unattended seconds, paused while hovered or focused. A toast never takes focus as it appears; when one that held focus leaves, focus goes to the toast now in its place, else to the region. The region is fixed over the page's lower corner — the full width between the 16 px gutters at 640 px and below — so a toast coming or going moves nothing, and it lets a click through where it holds none.

## The shell

`src/App.tsx` is what every screen mounts into. The top bar is design/'s `TopBar`: the name; **the workspace indicator** (`src/shell/WorkspaceIndicator.tsx`) — the path, how many services the workspace binds, and a filled dot, or a hollow ring and the words "Workspace unreachable", read from `GET /workspace` and saying so while that request is in flight, as a link that opens Setup; **the six screens as links**, the current one marked, each to its screen's bare address — but Pipeline's, which opens the last pipeline viewed (`src/pipeline/last.ts`), remembered per viewer in `localStorage` once its matrix has loaded, or the bare screen before any; the job stream's connection state when the page follows it, in `TopBar`'s status slot; and **the theme control** (`src/shell/ThemeControl.tsx`), a segmented control of System, Light and Dark. The theme sets `data-theme` on the page's root, or removes it for the system's choice (§ The design system), and is remembered per viewer in `localStorage`; every storage access goes through `src/shell/storage.ts`, guarded, and the page is right without storage — the choice then simply is not remembered. **Deferred**: the theme is applied in a layout effect once the application has mounted, so a stored light or dark choice that differs from the system's paints one frame in the system's theme first; removing that flash takes a script in `index.html` that runs before the bundle, which the content security policy's `'self'` rule makes a separate file.

**The bar never widens the page.** Too narrow for one line, its parts wrap onto further lines in their own order — the name, the workspace, the screens, the end with the theme — so the visual order stays the keyboard's, and nothing is hidden behind a disclosure: every name and every tab stop is the one a wide bar has. A workspace path longer than its line breaks inside itself; the screens wrap inside the nav. Each line keeps room — the name and the workspace a control high, the nav and the end bar-high — so the current screen's mark sits on the line's edge as it does on one line; at 640 px and below the screens' padding tightens, so at 390 px the six share one row. All of it is in `design/components/TopBar/TopBar.css`, and none of it moves a pixel while the one line fits. happy-dom lays nothing out, so the test asserts these rules; the widths are measured in a browser.

The indicator shows no benchmark count; Setup shows the workspace's counts, benchmarks among them.

Below the bar is the screen the address shows (`src/shell/screens.tsx`): Runs (§ The Runs screen), Pipeline (§ The Pipeline screen), Compare (§ The Compare screen), Replay once the address names a run or a job's partial traces (§ The Replay screen), the Editor (§ The editor), Setup (§ The Setup screen), and Replay at `#replay` in its empty state: the screen's name as the page's heading, then one sentence on the default path and the one action that leads on — a real link to the screen it names (design/'s `ButtonLink`), so middle-click and "copy link" work. A failed workspace read is shown above it as a section error with Retry — except on Setup, which shows it in its own Workspace and This build sections, where the workspace is. The shell hands every screen its read of `GET /workspace` — the one the build identity handshake judged — and two ways to read it again: in place, after a write that changes what it counts, so the top bar stays current, and from the loading state, for Retry.

**A change of view moves focus to the new screen's heading** — an `<h1>` with `tabIndex={-1}`, the no-route message's included — so a screen reader announces the view and the keyboard starts from it. The view is the screen and its path, `viewOf` in `src/routes.ts`, never the query: state within a view written to the address — Runs' selection, a selection corrected in place — moves no focus, so checking a box leaves focus on the box or the row. **Replay's view is its run** (`#replay/<run>`), or its job (`#replay/job/<id>`): the query shown and the run beside it are state within it, though the query sits in the path, so the arrow keys move through the queries and focus stays in the list. The load moves nothing: a deep link keeps the browser's own focus. The hook compares the view with the one the page loaded at rather than counting renders, because StrictMode runs a mount's effects twice; a test mounts the shell under `StrictMode` to hold it.

The shell reads the workspace, and opens the stream, again only when its client, its build or the stream's path change; the `reload` it is given is kept in a ref, so a parent passing a new function does not refetch or reopen anything.

**The four states** are `src/shell/states.tsx` beside design/'s `EmptyState`: `Loading`, only while a request is in flight and always a label, never a bare spinner (a request has no count to show); `ErrorState`, an `ApiProblem` rendered inline — its message, where a validation failure is, its hint and its code — through `InlineMessage`, never a modal, with Retry when the caller can retry; and `Resource`, which renders a request's `RequestState` as the loading, the error or the loaded state.

## The Runs screen

`src/runs/` is the first screen and the widest (the front-end design, § 3): what the store holds, **grouped by pipeline**, one row per run. A run is one pipeline on one benchmark, and its metrics are what that benchmark's ground truth allows (ADR-008).

**What it reads.** `GET /runs` once on mount, on Retry, and again whenever the address names a run the listing does not hold (below). **Only the answer to the last listing asked for lands**: an earlier request that answers later is dropped, so of two racing reads the newer wins. The read a newer one overtakes is also cancelled through its signal, and so is the one left when the screen goes, which saves the server's work. Two checks drop an overtaken answer, the count of the last one asked and the cancelled signal: a newer read moves the count before it cancels, so either suffices there, and the signal alone covers the screen going. A re-read that fails keeps the listing on screen and says so inline, with Retry; only a first read that fails replaces the screen with the error. **`GET /runs` is the only request the table makes** — the job queue is the page's (§ The job stream), and the launch panel and the job view read their own, below: each pipeline's shape comes in the listing's `shapes`, keyed by its canonical hash, so no `GET /runs/{id}` is made to draw one and a group heading is whole when it is first drawn — nothing loads into it afterwards and nothing moves under it. Whether a recorded name is still a workspace document comes in the listing too (`launched_as.held`, from the one listing of `pipelines/` the API makes for it), so the screen reads no `GET /pipelines` and a heading never changes after it is drawn. The listing's `unreadable` runs are shown above the table, each short id with the reason the store gave, never dropped. Loading is `Loading` ("Reading runs"), a failed listing is `ErrorState` with Retry, and a store with no runs is design/'s `EmptyState` with one sentence and the way to the Editor.

**The row model** (`model.ts`). The screen renders `RunRow`s and `RunGroup`s only; `rowsFromListing` fills them from `GET /runs`. A row carries its **source** — `{ kind: 'run', id }` or `{ kind: 'job', id, runId }` — its pipeline hash and **every** name it goes by, the name its launch record says it was launched as (`launched_as.name`, or null), its benchmark key and **every** name pinned to it, a status, its metrics in groups by family, a latency, a start time and a prefix relation. **A field the source does not carry is null — an empty list, for the names — and nothing is drawn for it**: the latency and start columns appear only when some row has one, a metric family's label only when the source says a family (`unknown` included), and no cell ever holds a dash for a metric the benchmark could not have produced. Every row of the listing is a `done` run; the job queue's rows fill the same fields (below). **The names are lists**, as the listing gives them, and **every one is shown, never one picked**: the benchmark is labelled by all the registry entries pinned to its digest, joined by commas (`beir/scifact, scifact-local`), or by its short dataset digest when none is (`dataset 331a9c8c4092`); the group heading links the name or names the group is headed by (§ Grouping, below). The start time is the run's own record (`started_at_ms`), drawn as a `<time>` in the Started column, and nothing when it is `null`. **Metrics are grouped by the family the listing sends** (`metric_families`, from `ragondin-metrics`' catalogue): `ranking`, then `answers`, then `unknown`, each group a labelled `role="group"` and each in the order the run recorded its metrics. A ranking metric prints four decimals; an answer metric is a percentage to one decimal under the design's name (`EM 41.2`, `F1 49.1`: `metricLabel`); a metric of family `unknown` — a name the catalogue does not know — is shown under that label with its stored name and its value as stored, never hidden and never rounded by a rule nothing gave it. A name the listing gives no family for reads as `unknown` too. The browser keeps no copy of the catalogue to guess a family from, since that copy would drift from the crate that computes the metrics; `metricLabel` names the two answer metrics for display only. **The latency** is the listing's `median_query_latency_nanos`, in the column headed "Median query latency" — the median over the run's queries of each one's own latency, never the run's wall time from start to finish — in whole milliseconds, or to two significant figures under ten (`formatLatency`) so a fast pipeline does not read as 0 ms; the column appears only when some row has one, and a row without one draws nothing in it.

**Order.** `rowsFromListing` sorts the listing **most recent first** by `started_at_ms` (`byMostRecent`): a run whose start is unknown comes after every run whose start is known, never before one, and ties — unknown ones included — are broken by run id, so the order is stable from one read to the next. Groups then come in the order of their first row, so the group with the most recent run is first.

**The hand-off to the job queue and to prefix runs.** The row model is the seam, so neither needs a second row shape. A run of the store is `done`; a job's row is `queued`, `running` (`done` out of `total` queries, as the queue reports them — the chip prints the count and draws its meter from it, never a percentage of the client's; `starting` until the first query gives the total), `done`, `failed` (the node, when named, and the error) or `cancelled`. **Opening routes by source**: a run opens in Replay (`#replay/<run>`); a job opens at its own address, `#runs/job/<id>`, never as a run it is not. **A run is a prefix** of the parent its launch record names when the record carries `prefix_of`; otherwise of every current document the listing's `prefix_of_documents` names — the structural test the API asks of every run (`runtime/ragondin-api/ARCHITECTURE.md` § Prefix runs), so a prefix written by hand and run from the command line is one too. Its row's `prefix` is those parents and the node it stops at, and it carries design/'s `PrefixLabel`, "prefix of <parent>, up to <node>" — two parents both named, more as the first and a count ("prefix of hybrid (and 2 others), up to rerank"), every one in the label's title and in hidden text. **A record never hides the structural relation** (ADR-C39 § 4): when the record names a prefix and the structural test names other documents, the row draws that second fact beside the label, "content: prefix of hybrid-fork, up to rerank" (`contentPrefix`); when it names the record's parent alone it says nothing new and is not drawn, as the group's other-fact label is not when it repeats the heading. Its record names the parent, so the grouping rule below puts it in the parent's group, and a structural prefix with no record and no hash match goes there too; a parent with no run here gets a group of its own, with no shape, so the prefix run is still shown. A job submitted up to a node is a prefix of the pipeline it names, labelled alike.

**The job queue's rows** (`jobRows.ts`, `jobRow.tsx`). `rowsFromJobs` draws the queue's run jobs — a download has no row here, nor a job a person dismissed (`dismissed_at_ms`) — as `RunRow`s whose source is the job, live work first: the running job, then the queued ones in the order the worker takes them, then the ended, newest first. **The live jobs are the Queue**, a table of its own above the runs under the heading "Queue", in that order, each row naming its pipeline in a first column, since no group heads it; it is drawn only while there is live work. An ended job knows the name it was launched as, so it sits in that name's group beside the runs launched as it; it knows neither its canonical hash nor whether the workspace holds the name now, so the heading, its shape and whether the name is held are the store's runs' when the group has any — a group of jobs alone draws no shape and says the name is "no stored run yet, so not linked". A benchmark name a run of the store pins takes that run's digest, so one filter chip holds both. A row shows **the identity its job announced**, short, as a link to the job, labelled "announced"; its chip; and, in a detail cell one small control high whatever it holds (`.rg-runs__job`), what the state offers: a queued job its place ("queued, next", "queued, 2 ahead") and **Move up**, **Move down** and **Cancel**; a running job the median query latency the queue reports on each tick ("1.84 ms / query", never computed here), the time elapsed since the worker took it, read from the clock each second and never a live region, and Cancel; a failed job its error once — colour is never the only carrier, and the chip already names the node — as the launcher wrote it, what it quotes in backticks set as code (`ErrorWords`), **Fix in editor** to the failing node (`#editor/<pipeline>/node/<node>`) when a node failed, **Resubmit** and **Dismiss**; a cancelled job Resubmit and Dismiss; a done job "Filed; reading it from the store…" while the store is read again for its run, or, when the queue names no run filed, says so and reads nothing. **A job with faults** says how many beside its identity ("1 fault", `.rg-runs__fault`, in the warning's ink and in words), each reason in the count's title, and its name ends ", 1 fault"; never on its chip, which says where the job stands, and never a live region — the job's view announces them. Its live figures are the row's own, never the store's latency and start columns, so a first tick adds no column to the table. A done job's row hands over to its run's once the store holds the run — the screen reads `GET /runs` again whenever the queue has a done run job whose run the listing lacks — and an ended job's row goes once the store holds its announced run or a later job announced the same id (a resubmission took it over). **When the run is filed under another id than it announced** (`id_mismatch`), the run's row says both and why (`withAnnounced`): "announced as …; filed under this id because what ran differs from what was announced" — the job says it; the client compares nothing. While the stream is down, a live row's words end "· last known" and the line above the table says so — present while the page follows the queue, empty or not, one line high and two at 640 px and below, so the rows never move as the stream drops and returns. The row takes the table's keys like a run's — Enter opens the job — and its name says where the job stands ("…, running"), never its count, so a tick does not re-announce it; every control in it is a native button in the tab order, named for its row ("Cancel run a1b2c3d4e5f6").

**Cancel, reorder, resubmit, dismiss.** Each is a request whose outcome the stream then says. **Dismiss** sends `POST /jobs/{id}/dismiss`, and the row goes once the stream's `dismissed` event carries the job back with its time; the queue still lists it, and its partial traces stay. **Cancel** sends `DELETE /jobs/{id}`; the row says "cancelling…", on the same button, refused, until the queue says the job ended — a queued job at once, a running one between two queries — and the cancel is forgotten once it has. **Move up** and **Move down** send `PATCH /jobs/{id}` with the place among the queued run jobs, refused at either end with the reason, and the rows follow the API's answer — the queue in its new order — not the request, until the stream's `reordered` (or `resync`) events say the order themselves, and win. An answer is applied only when the stream has said no order — a `reordered` or a `resync` — since its request left, so an answer overtaken by a later order is never shown. The server publishes a reorder's events before it answers, but the stream and the answer can reach the browser in either order, so a dropped answer may leave the rows briefly without its move: transient, and corrected when that move's own `reordered` events arrive. **Resubmit** sends the job's submission again as it was — the same pipeline name, benchmark and `up_to`. The API announces the id again from what those name now: the same one while nothing they name has changed. Focus is managed across each: a Cancel that had focus hands it to its row's Resubmit once the job ends; a Move keeps it on the same button of the moved row; a Resubmit hands it to the new job's Cancel; a Dismiss, once its row goes, hands it to the row after it in its table, or, when it was the last, to the table's heading "Runs" — visually hidden, out of the tab order — each only while focus is still where the person left it or was dropped with the control. A refusal is the API's detail, hint and code below the table, and `run_exists` is a run or job to open, never an error.

**The launch panel** (`LaunchPanel.tsx`), opened by **Launch…** in the bar — or beside the empty state's action — and taking focus as it opens. Its fields are `ragondin bench`'s arguments (the front-end design, § 2): the **pipeline**, from `GET /pipelines`, one that does not validate listed as such with the validator's words on the field, and Launch refused; the **benchmark**, from `GET /benchmarks`, ready ones only (`ready` and `local`), each with the ground truth it carries; the **bindings in force**, from `GET /services`, read-only — the API snapshots the workspace's own at submission and the request carries none (`runtime/ragondin-api/ARCHITECTURE.md` § Choices made here) — and the **store**, the workspace's, shown, not chosen. Each listing has its own loading and error state. **The benchmark field offers what the pipeline can be scored on**, by what it ends in — the listing's `ends_in_answer` — among the ground truths `GET /benchmarks`' `scorable` lists for that output, `ragondin-benchmarks`' `CarriedPieces::scorable` served by the API and never restated here — the API leaves a benchmark that carries no ground truth out of both lists, so the panel only reads them. The benchmarks left out are named below the field with why, in words drawn from those served facts alone — each one's ground truth, and the ground truths what is launched can be scored on ("Not offered: squad/dev, which carries reference answers: a pipeline that does not end in an answer can be scored only on a benchmark whose ground truth is qrels."), a note the field names in its `aria-describedby`; a pipeline that does not validate filters nothing, being refused whatever the benchmark. It shows **the pipeline's content hash** once the document validates, as the listing gives it, labelled "Content hash" (a run's identity is derived from it, so it changes when the pipeline does), and **the run id the API announces** once queued ("run … announced", and Open, to the job): the panel never computes an identity (INV-8). **Launch** sends `POST /runs` with the pipeline's name and the benchmark, says "Launching…" meanwhile, and becomes **Queued** — refused, with the reason — until another pipeline or benchmark is chosen, or until the stream says the queued job ended, when Launch is offered again. **A refusal's reason is on the page**: the refused button's reason is a caption beside it (design/'s `Button` with `showReason`), the one description a screen reader hears. An empty field says so — "No pipeline yet", "No ready benchmark" — rather than standing blank, and **Close** beside the action closes the panel as **Launch…** does, focus returning to Launch… through its ref. A `run_exists` message names a run by its short id. `run_exists` is shown as what it is, never as an error: "A run with this identity already exists." or "… is already queued or running.", with Open to where its `link` leads — the run in Replay, the job in Runs. `pipeline_invalid` and `impl_not_in_build` are shown on the pipeline field, with the node and the hint; `service_unreachable` (and any binding refusal) on the bindings; a benchmark refusal on the benchmark field; anything else below the panel. **A choice made here: the panel lives on Runs**, not yet in the editor's inspector footer, where the design places it: a launch takes a workspace document as it is on disk, and the canvas reaches the disk only after its debounce, its validation and any prompt, so a panel in the editor would launch something other than what the canvas shows while a change is pending. The editor hands off to it instead (§ The editor).

**Up to a node** — the address `#runs?launch=<pipeline>&up_to=<node>`, which the editor's "Run up to this node" and "Run up to here" open, the panel taking focus — the panel launches the pipeline cut at that node, a pipeline of its own (`runtime/ragondin-api/ARCHITECTURE.md` § Prefix runs). It offers that pipeline alone, labelled with `PrefixLabel`; it shows no hash, since the parent's would stand in for the cut's, and says the prefix's identity is announced when it is queued; **Run the whole pipeline** drops `up_to` from the address in place. The benchmark field offers the ready benchmarks the cut can be scored on, judged as for a whole pipeline (above) by what the cut ends in, as the API says it: `GET /pipelines/{name}`'s `ends_in_answer_up_to`, read in this mode only; until it is read, or if it cannot be, the narrower offer stands. The ground truth is `GET /benchmarks`' `ground_truth`, the listing the panel already reads. The benchmarks left out are named below the field with why ("Not offered: squad/dev, which carries reference answers: a prefix that does not end in an answer can be scored only on …"), a note the field names in its `aria-describedby` beside its help line. **Launch** sends `up_to` with the pipeline and the benchmark. A refused cut — `prefix_node_not_found`, `prefix_is_whole_pipeline`, `prefix_ends_in_context` — is shown on the pipeline field with its node, `prefix_not_scorable` on the benchmark field. Closing a panel the address opened takes `launch` out of the address, so a reload does not open it again, and a selection written meanwhile keeps it.

**On a benchmark** — `&benchmark=<name>` beside `launch`, which the Pipeline screen's Run opens (§ The Pipeline screen) — the benchmark field opens on that benchmark, and **Launch** sends it. A named benchmark the field does not offer is never replaced by another: the field shows it with why — "… — unknown", a name `GET /benchmarks` does not list; "… — not ready", listed but not on disk as expected, with Open Setup; "… — not offered", ready but one the pipeline, or the cut, cannot be scored on — the help line says the field holds it beside the ready ones, and Launch is refused with the reason until another benchmark is chosen. **Run the whole pipeline** keeps the benchmark.

**On several benchmarks** — the key repeated, `&benchmark=<a>&benchmark=<b>…`, which "Launch the N missing runs" opens — the benchmark field becomes the list "Benchmarks", one line each in the address's order: its ground truth, or "not launched:" and why, in the words above (not a benchmark of this workspace; not ready, with Open Setup; cannot score this pipeline, or this prefix). The pipeline, its hash and the bindings in force are shown once, above them all, and there is **one confirmation**, "Launch N runs", N the benchmarks that can be launched — "Nothing to launch", refused with why, when none can. It sends one `POST /runs` per launchable benchmark, one after another in that order, and **says each outcome on its benchmark's line**: the run announced, with Open to its job; `run_exists`, "already exists" or "already queued or running", with Open to what holds it; any other refusal, "refused:" and the API's detail, hint and code. A refusal stops nothing: the benchmarks after it are still sent. A partial failure is said as one: the queued runs stay queued and are not taken back, and a status line counts what came of the whole ("1 queued, 1 refused."). The button then offers **Retry the N refused**, one confirmation that sends the refused alone — never a benchmark queued or already held — or, with none refused, reads **Submitted**, refused; nothing is retried by itself. While the runs are sent the button is busy, so a second press sends nothing, and the pipeline field is locked, since the answers in flight are that pipeline's. **Closing the panel mid-way does not stop the runs not yet sent**: they are sent all the same, and the panel says so while they are; their jobs appear in the queue's rows as the stream announces them.

**The job view** (`JobPanel.tsx`), at `#runs/job/<id>`, above the table, its row marked (`aria-current`): what was submitted, the identity announced, when it was queued, where it stands; a failure's error, once, as on its row; a done job's run, with Open in Replay, and both ids when they differ. A failed or cancelled job says how many queries' traces it kept — the queue's count, `partial_traces`, never counted here — where they are, `jobs/<id>/partial/` in the workspace, never in the store, and leads to Replay over the job (`#replay/job/<id>`, § The Replay screen) — unless no query completed: the count includes the query a node failed on, so a job failed at a node that kept one trace says no query completed before it failed and offers nothing to replay; a job that kept none — a crash keeps none it can vouch for — says so and offers nothing to replay. **The faults the queue reported beside the job**, of a run or a download, are design/'s warning `InlineMessage` below its facts: "1 fault beside this job; it did not stop it", then each reason with when it was reported, inside a polite region (`.rg-job__faults`, `role="status"`, `aria-atomic="false"`) that is there, empty, before the first fault, since a live region inserted already filled may go unannounced. It is the one live region there — the warning inside it is rendered `live={false}`, no status of its own — and it is not atomic, so a fault the stream brings while the view is open is announced politely, once, as what was added, never the whole list again. It is never an alert, since the job goes on. The view is keyed by its job, so another job's view starts from its own read, never from the last one's. The job is the queue's when the stream holds it, else `GET /jobs/{id}`'s answer — a pasted link may name a job before the stream's first `resync`, or one it never gives. Close returns to Runs, keeping the selection. The view takes focus when the address moves to another job, not on load.

**Grouping** (`groupRows`), ADR-C39 § 4's rule: a run is grouped by `launched_as.name` when its record has one; otherwise by its `pipeline_names`, every one; otherwise, for a prefix the structural test found, by the documents it is a prefix of; otherwise under its short hash. One name is one group whichever fact gave it, so a run without a record whose one hash match is `hybrid` sits with the runs launched as `hybrid`; several hash matches are one group headed by all of them; the three kinds are kept apart in the group's key, so a document named like a hash is never that hash. One canonical form can therefore sit in two groups: runs launched as `hybrid` under `hybrid`, and runs without a record whose hash `hybrid` and `hybrid-fork` both hold under "hybrid, hybrid-fork" — the facts differ, and the grouping follows them rather than merging them. **Each row shows the other fact as a secondary label**, after its hash (`otherFact`): under a recorded name, the current documents holding its content ("content held by hybrid-fork") or "no pipeline in the workspace matches this run now", a word apart from the hash so it reads and copies as words; a row's identity and its labels are one wrapping box (`.rg-runs__run`), so the table fits a 1440 px screen with every column in view; under the hash matches or the hash, "launch not recorded", or "launch recorded without a name" for a record that names no pipeline. Under a recorded name whose one current document is that name itself, the row draws no label: the heading already says it. A choice made here: the label is the row's, not the heading's, because one recorded name's group can hold runs of several contents, and runs with and without a record — one label per group would have to pick among them or merge them, and the two facts are never resolved into one. It is text drawn with the row, so nothing loads into it and nothing moves. Facts only: no label says a run is an earlier version of anything (ADR-C39 § 7). Groups come in the order their first run appears, runs in that order. The table is design/'s `Table`, one semantic table with a `tbody` per pipeline under a row-group header, so assistive technology reads each run under its pipeline. The header (`GroupLabel.tsx`) holds the name or names the group is headed by, each a link to `#pipeline/<name>` (or, with none, "pipeline" and its short hash as a link to `#pipeline/<full hash>`), the shape, the count of the runs the store holds — a job beside them is not one, and a group of jobs alone draws no count — and "Edit" (`#editor/<name>`) for the first name held exactly, which none is offered for when no name is. A name the listing says is not held exactly is not a link, and says why in words of its own, each name for itself (`RunGroup.held`, one per name): `gone` — its document deleted or renamed since the launch, whose address lands on a pipeline that is not found — is written with "no longer a document in this workspace"; `other_case` — another stored name differs from it only in case, so the API refuses its address as a case alias, whether or not it is also stored as given — with "refused: another spelling differs only in case". A record that says neither nor `exactly` — `unchecked`, which `GET /runs` never sends, or nothing — fails closed: unlinked, "no stored run yet, so not linked" — a name only jobs go by. A hash match is a current document, so it is held unless the listing names it among the run's `refused_pipeline_names` — `hybrid.yaml` and `Hybrid.yaml` both stored, a hand-made pair on a filesystem that keeps case, are both hash matches and both refused — and is then `other_case`, unlinked; the screen applies no case rule of its own, only the API's list. **The shape** is design/'s `FamilyTile` per node, its glyph named, in pipeline order: every node after the nodes it reads, ties in the graph's canonical order (`shapeOf`). Which tile a configuration's family takes is design/'s `familyOfComponent`; a family it draws no tile for — an extension node — is written as its word. The shape is the listing's for the canonical hash of the group's most recent run of its own — under a recorded name, the runs may hold several contents, and the heading draws the latest; a group with no row of its own — a prefix run's parent — draws none, and so does a pipeline the listing carries no shape for (none of its stored documents lowers).

**The selection** (`selection.ts`) is the state Runs hands to Compare. **It lives in the address**, `#runs?sel=<id>,<id>…`, so a link or a reload reproduces it, and it is written with `{ replace: true }`: checking a box is state within the view, not a move Back should undo, and the shell moves no focus for it (§ The shell). Its rules: run ids in the order they were checked; **one benchmark** — once a run is checked, every run on another benchmark is refused; **at most five**, a baseline and four (the front-end design, § 3) — once five are checked, a sixth is refused; a job is refused — a failed one with "Failed". A refused box is disabled with **a short reason** ("Other benchmark", "Five selected", "Failed") as its description, and the selection's rule is said **once**, in full, below the table, rather than repeated on every row. **Nothing that comes and goes as boxes are checked sits above the table** — the rule, a failed re-read — so the rows never move under the pointer between two clicks. An address carrying what no click could have selected — a duplicate, a run on a second benchmark, a sixth — is corrected in place to what could have been. **An id the listing does not hold is not dropped on sight**: the run may be newer than the listing. The screen reads the listing again, keeping the current one on screen, and drops the id only once a listing asked for while the address named it still lacks it; meanwhile the id stays in the address but does not count toward "Compare N selected", nor is it passed to Compare. "Compare N selected", the screen's one primary action, opens `#compare/<ids>` in selection order and is refused, with its reason, below two runs. "New pipeline" is the secondary action, a link to the Editor.

**What it owns**: the benchmark filter (design/'s `FilterChip` per benchmark, with its count), in the address (`#runs?bench=<key>…`, written in place), so a link or a reload shows the same rows; nothing else. **What it hands on**: to Compare, the selected ids in order; to Pipeline, a pipeline's name, or its hash when it has none; to Replay, a run id (`#replay/<run>`), from the run's short hash, which is a link, and from Enter on its row; to the editor, the one run selected, through "Fork this run" in the bar (§ The editor), refused, saying why, unless exactly one run is selected.

**Keyboard.** The table is **one tab stop** (design/'s `Table` with `onOpen` and `onToggle`): the up and down arrows, Home and End move between the rows, Space toggles a row's selection when the run can be selected, and Enter opens it. A row is named by its run and benchmark ("Run a1b2c3d4e5f6 on beir/scifact", with ", failed at rerank" on a failed one) and by its selection state — ", selected", or ", cannot be selected: Other benchmark" — because focus stays on the row when Space toggles it, and a change of its name is what a screen reader announces; its checkbox by the run it selects ("Select run a1b2c3d4e5f6 on beir/scifact") beside the benchmark as its visible label. The checkbox and the hash link inside a row leave the tab order — the row takes their keys — and a click still reaches both.

## The Pipeline screen

`src/pipeline/` is the second screen (the front-end design, § 3): **one pipeline, all its runs, as a matrix of node × benchmark**, read from one `GET /pipelines/{name}/matrix` — every cell a per-node figure the API reads from a run's trace, no new kind of run.

**What it reads.** `GET /pipelines/{name}/matrix` with `include_available`, so every benchmark the registry knows has a column, and one no run measured reads `not run yet` in every row; the name is the address's, `#pipeline/<name>` (§ The router and the URL state), so a reload or a pasted link reads the same pipeline. It reads again whenever the address names another pipeline, and **only the answer to the last matrix asked for lands**. `GET /pipelines` once, for the selector. Loading is `Loading` ("Reading the matrix of <name>"); a failure — `pipeline_not_found` included, which is what a Runs group named only by its hash reaches, since the endpoint takes a document's name — is `ErrorState` with Retry. A pipeline with no run at all is design/'s `EmptyState` and the way to launch it, the Editor on that pipeline; before a pipeline is chosen (`#pipeline`), an `EmptyState` with the selector, or the way to the Editor when the workspace holds none. **Nothing is computed here**: the figures, the gains, the reasons — whether the pipeline can be scored on a benchmark included, `not_scorable`, which the API asks of `CarriedPieces::scorable` — which run fills a column, a column's failed attempt, the feeding runs and `missing` are the API's (`runtime/ragondin-api/ARCHITECTURE.md` § The pipeline matrix); `model.ts` only lays them out, and `fixtures.ts` is the answer the tests read: hybrid-rerank-gen on beir/nfcorpus, beir/scifact and squad/dev, and its variants.

**The header.** The pipeline selector, every document of the workspace by name, choosing one a move to its view; "Edit", into the editor on this pipeline; the "Ranking metric" selector, over the ranking metrics the matrix's cells carry, opening on `defaultMetric` (`src/metrics.ts`), the one rule Compare's stage line, Compare's per-query metric and Replay open on — ndcg@10, else the first — local and unremembered, the one state the screen owns; the shape, labelled on screen "Shape, node by node", as design/'s `FamilyTile`s in the rows' order, each beside its node's name and its family in words — the glyph hidden from assistive technology, since the words say it; and the subtitle saying how many runs the matrix is derived from, that each column is the most recent run on its benchmark and that nothing is stored, with the canonical hash.

**The matrix** (`Matrix.tsx`) is design/'s `Table` with `rowHeaders` and `region`. **Rows** are the API's, the pipeline's nodes in topological order: the family tile, the node and the metric the row reads — the chosen ranking metric on a ranking row, `EM, F1` on the generator's (`metricLabel`), none on a row no metric reads. A family no tile draws is written as its word. A row no metric reads — the context builder — is one sentence spanning every benchmark: not scored is structural, so a row spans when it holds a `not_scored` cell and every other cell only says the node was not measured there (`not_run_yet`, `prefix_stops`, `not_run_on_this_version`), which `include_available` and a prefix column make the usual case; any other cell keeps the row as cells. No judge row is drawn: the API reserves it and serves none until the judge exists. **Columns** are the API's, in its order (by benchmark name, never by score): every benchmark name pinned to the digest, or its short digest; the status — `measured`, `up to <node>` for a column a prefix run fills, `earlier version only` for one only a run of earlier content measured, each design/'s `StatusChip`, or the words `not run yet`, or `cannot be scored` for a column whose every cell is `not_scorable`; a column whose most recent attempt failed (the API's `failed_attempt`) reads a `failed` chip, "last attempt failed", and "open", a link to that job in Runs (`#runs/job/<id>`) — in place of `not run yet`, which it says more than, and beside any other status, `cannot be scored` or `earlier version only` — with a warning chip beside it when the dataset check is not verified, in the words of what it found — `dataset absent`, `dataset differs`, `dataset unreadable`, `index differs` — its detail below the matrix; and what the ground truth carries, or that it is read once a run measured the benchmark. **Cells** are two lines, always as tall, so no state and no change of metric moves a row:

- **measured**, on a ranking row: the value in four decimals, quiet beside a gain — in ink where no gain stands beside it (a first stage, stages guessed, unstaged, no gain on the metric), since it is then the cell's one figure — and on the second line the gain over the previous stage, which is what is emphasised — in ink, signed, with an arrow — because benchmarks differ in difficulty and the best value would almost always sit in the same column. Each `MatrixGain` is said as it is: `over_previous_stage`, its gain on the chosen metric, or "no gain on <metric>"; `first_stage`, "first stage", nothing before it to gain over; `ambiguous`, "stages guessed" and no number, since which stage came before is a guess; `unstaged`, "not a ranking stage". **The best gain of a row is bold** (with "best gain in this row" for assistive technology), every column of a tie, and only when two or more cells of the row have a gain; **the best value never is**. **This assumes a higher gain is better**: the matrix serves no direction with a gain, and the API serves a gain only for a metric its catalogue gives a direction, every entry of which improves upward — `eval/ragondin-metrics/src/catalogue.rs`'s test `answers_and_ranking_metrics_carry_their_family_and_direction` asserts it, so a lower-is-better metric fails there first, and adding one means serving the direction with the matrix, as `POST /compare` does. On the generator's row, `EM 41.2 · F1 49.1`, unstaged.
- **empty**, saying why in the cell: `no qrels` and `no reference answers`, **hatched** beside their words — never measurable on that benchmark; `not run yet` — **one Run control per benchmark not run**, in its first `not run yet` cell outside a spanning row, every other such cell saying it in words, so a dozen registered benchmarks are a dozen tab stops rather than dozens; in a column whose last attempt failed the same cells read `last attempt failed`, the Run kept to try again, since a failure fills nothing; `cannot be scored`, **hatched**, and no Run — the pipeline does not end in an answer and the benchmark is scored on reference answers, so a run there would be refused; `not run: the prefix run stops at <node>`; `not run on this version` with the run of earlier content, a link to its replay; `unverified`, which claims only that the run's dataset is not verified on disk, whatever the check found; `not scored`; `no figure`.

**The hand-off to the launcher** is `Launch` in `Matrix.tsx`: a function given `{ pipeline, benchmarks }`. The screen's is `launchInPanel`, which opens Runs' launch panel on the pipeline, whole, and those benchmarks — `#runs?launch=<pipeline>&benchmark=<name>…` (§ The Runs screen) — so a Run queues nothing by itself: the person sees the pipeline's hash, the benchmark and the bindings in force, and presses Launch there. There is one launcher, the panel, and no launcher module is imported here; a test passes its own `Launch`.

**Below the matrix.** The runs that feed it (`FeedingRuns.tsx`), the most recent first as the API lists them: each a link to its replay, its benchmark and start, design/'s `PrefixLabel` on a prefix run — "prefix of <pipeline>, up to <node>", the API's `prefix_of`, by its record or by structure — whether it fills its column, and ADR-C39 § 4's two facts side by side, never resolved into one name — what its launch record says it was launched as ("Run under the name <name>", "Run as a prefix of <name>, up to <node>", "Run under no name", "No record of the name it ran under"), and which current documents its content is ("Configuration matches <names> now", or "no pipeline in the workspace"). A run whose content changed since its launch reads "Launched as <name>; content since changed" — ADR-C39 § 7's wording, kept as that decision states it — or "A prefix of an earlier version of <name>" for one its record launched as a prefix, with its parameter difference as the API gives it, the current document's value first — a `Table` with `region`, so on a phone, where it scrolls sideways, its scroll box is a named tab stop as the matrix's is. Then the verdict, one sentence of counts — on how many benchmarks the pipeline is measured, how many of them only up to a node, how many cells wait for a run of the whole pipeline — and the screen's **one primary action**, "Launch the N missing runs" ("Launch the missing run" for one), N the runs it launches — one per benchmark of the API's `missing` a launch can fill, each name once (`launchableBenchmarks`), never the cells, since one run fills every missing cell of its column — while the verdict counts the cells, and a column no benchmark name is pinned to apart, since it has nothing to launch on; absent when N is zero. It opens the launch panel with every launchable column's benchmark at once, each name once though two columns carry it — a column a prefix run fills, or one only earlier content measured, included, since what fills it is a run of the whole pipeline — where one confirmation sends one run per benchmark (§ The Runs screen). A column it cannot launch, one no benchmark name is pinned to, is listed below it with why ("Not launched: dataset 0b1c2d3e4f5a, which no benchmark name is pinned to, so there is nothing to launch it on.").

**Keyboard and assistive technology.** The matrix is one semantic table, named "<pipeline>: each node on each benchmark": a column header per benchmark and a row header per node, each data cell under both, and a cell's state in its own text — a hidden rest of the sentence where the visible words are short ("first stage — nothing before it to gain over", "no qrels — never measurable on this benchmark"). Its scroll box is a named region and a tab stop, so the arrow keys scroll a matrix wider than the screen while the row headers stay in view. The column headers stick to the top of that scroll box, not of the page: the box is their sticky container, so on a page scroll they leave with the matrix; the Run buttons, one per benchmark not run, and the run links follow in reading order. A change of pipeline is a change of view, so the shell moves focus to the screen's heading (§ The shell); a change of metric is not.

## The Compare screen

`src/compare/` is the screen that answers "what did I change and what did it do" (the front-end design, § 3): a baseline and up to four runs of one benchmark, read from **one** `POST /compare`, laid out top to bottom as the run bar, the metrics, the stages, the latency, the per-query histogram, the configuration, and the verdict that ends the page.

**What it reads.** `POST /compare` with `{run_ids, baseline}` from the address, `#compare/<id>+<id>…?baseline=<id>` (§ The router and the URL state), so a reload or a pasted link compares the same runs against the same baseline; and `GET /runs` once, for the runs that can be added and to read the address's runs back. **An address writes a run by its 12-character prefix** where no other run of the listing starts with it, else in full — Runs' "Compare N selected" and every move Compare makes write it so (`addressIds`) — and every address waits for the listing, which reads each prefix back to the one run it names (`resolveAddressIds`) — the screen keeps no rule of its own for what a full id looks like; one the listing cannot resolve, or a listing that fails, is compared as written, and the API says what it names. Links into Replay still carry full ids: Replay reads no prefix. **Only the answer to the last comparison asked for lands** — a pairing's answer included, which is a comparison like any other: one overtaken by a newer comparison is dropped. A comparison read that is overtaken — by a new address, a pairing, or the screen going — is also cancelled through its signal, and its answer is dropped by both the count and the cancelled signal; **a pairing's post is never cancelled**, since it writes and the API may keep it whether or not its answer lands. A pairing that overtook a comparison read in flight and is then refused asks for the address as it stands again, since nothing else would land and the sheet would stay busy. An overtaken pairing the API answered was still kept on disk, so every answer held for reuse is forgotten, the address as it stands is compared again — the newer comparison may have been read before the pairing was written — and the panel confirms the pair, saying the comparison shown was asked for after it; an overtaken refusal it says nothing of. A run added builds its address from the address as it stands when the answer arrives, never from the one it captured, so a baseline changed meanwhile is kept. While a newer comparison is read — a new baseline — the one on screen stays rather than the page collapsing to a loading line and back: the whole sheet is `aria-busy`, and a status line that is always present says "Comparing again…" and empties again. Fewer than two runs in the address is design/'s `EmptyState` and the way back to Runs, carrying what was chosen; an address with two or more runs and no baseline, or one it does not compare, is corrected in place to the first run. `runs_not_comparable` — runs of two benchmarks, or more than five — is its own state, the API's detail and hint and the way back to Runs; any other failure is `ErrorState` with Retry. Nothing about a comparison is computed here: the table, the best of each row, the deltas, the matrix, the stages, the pairing, the bins and their bounds, and the latency medians are the API's (`runtime/ragondin-api/ARCHITECTURE.md` § Compare). `model.ts` only lays them out, and `fixtures.ts` is the answer the tests read: a dense-only baseline, hybrid and hybrid-rerank on beir/scifact.

**The run bar** (`RunBar.tsx`): each run as design/'s `RunSwatch` — its slot, the baseline first and then A to D in the answer's order, its workspace pipeline's name, and its hash, which copies the full id — with a remove button, refused with its reason when only two runs remain. A run's pipeline is the one whose pairings the API applies to it — its launch record's name, else the one document holding its hash (`runtime/ragondin-api/ARCHITECTURE.md` § The manual pairing); a run whose pipeline the API reports as `null` is named by its short pipeline hash, never by a guess. The baseline selector writes its choice in place, as Runs writes its selection: state within the view, no focus moved (§ The shell). "Add a run" offers only runs of the listing on the comparison's `dataset_version` that are not compared yet — no other benchmark is offered — each named as the baseline selector names a run, its pipeline then its short id ("hybrid · run 72e8d571e561"): the name its launch record gives, else its first matching document, by Replay's `runName`, else its short pipeline hash, and it and the baseline selector name a prefix run with `PrefixLabel`'s words, "prefix of <parent>, up to <node>", read from the listing by Runs' own rule (`prefixText` in `src/runs/model.ts`); and **compares with the new run before writing it to the address**: the API's answer moves the address, and its refusal — the sixth run's ceiling message — is shown in place beside the control, with the comparison still on screen. While it adds, the button keeps its word, so its width does not move the button beside it. "Replay side by side" is shown refused, with its reason: Replay's side-by-side address names one query (`#replay/<run>/q/<query>?with=<run>`), which the histogram's list provides.

**The charts**, each design/'s `ChartFrame` with its table alternative (§ The design system) — the grouped bars and the stage line name the metric table and the stage table shown below them (`tableBelow`) rather than offering a copy of each behind "Show as a table":

- **Grouped bars**, one group per metric read on one 0–1 scale — higher is better and every recorded value is in [0, 1]; a latency is not, and stays in the table, so no chart needs a second axis — the API's best per group labelled with a star and its value.
- **The stage line**, for one metric the stages carry (the "Stage metric" selector, opening on `defaultMetric` in `src/metrics.ts` — ndcg@10, else the first — the rule Pipeline and Replay open on): per run, the API's best value at each stage it kept, in its order, labelled by a pair's label where a pair drawn by hand named the row. A run without a stage has no point there and the line breaks — the hover layer and the table say "no stage here" — and a stage present without a figure for the metric says "no figure". Where a stage holds several nodes — the retrieval legs — each node's value is a hollow mark of its own beside the line through the best.
- **Latency per node**: each run's nodes stacked by their median duration in milliseconds, in the API's canonical order, each in its family's pigment (design/'s `familyOfComponent`), the legend the families' tiles and names; no run ink appears in it.
- **The per-query histogram**: one run against the baseline (a run selector when there are several) on one metric (the "Per-query metric" selector, opening on `defaultMetric` — ndcg@10, else the first — as the stage line does; every per-query delta is of a ranking metric), the API's seven bins with their counts, its bounds written as ranges ("below −0.3", "−0.3 to −0.1") and a bin's arm read from its name. The edges are the product's (the front-end design, § 3), and the API carries them with each bin; nothing here writes them. A bar opens its list of queries below it, one a line, the largest change first (`queriesByDelta`; ties in natural order, q9 before q10), each with its id, its text and its delta, each a link to `#replay/<run>/q/<query>?with=<baseline>`. A query's text is the dataset's, the same in every run of the benchmark: `GET /runs/{baseline}/queries` is read once, the first time a list opens, and a query whose text is not known yet or not served is named by its id alone. The section's caption says how the bars are made in the reader's words: seven bins from much worse to much better.

**The tables** (`tables.tsx`): the metrics, every row the API sent with each run's value, the best in bold by the API's `best` — every column of a tie — and each delta against the baseline as design/'s `Delta`, coloured, signed and worded, its meaning read from the metric's `direction`; a metric the API gives no direction (`null`: a name its catalogue does not know) has no best and its delta is signed alone, with no colour, arrow or word, since it is neither better nor worse; the stages, each run's nodes at each stage or "no stage here"; the parameters not identical across the runs, as the API lists them, each value written with its kind (`src/parameters.ts`: a float with its fractional part, text that would read as another kind in quotes), so `60` and `60.0` never read alike, each value that departs from the baseline's a `<mark>` with "(differs from the baseline)" for assistive technology. A node some run lacks — the API's `partial_nodes` — is **one row**: its Node cell names it and the runs holding it, "rrf only in A and B" by the run bar's letters (`onlyIn` over `runSeries`), its Parameter cell says "whole node", since the row is the node itself and not one of its parameters, and each run holding it written with its family and implementation ("fusion · rrf") and each other "no such node", never as rows of unset parameters (`configurationRows`); a parameter of such a node is kept only where the runs holding the node disagree, and a run without the node reads "no such node" there too. A ranking metric prints four decimals, a metric where lower is better one, a metric with no direction as stored — as the Runs screen prints a metric of family `unknown` — and a delta that prints as zero reads as unchanged, never as a coloured "+0.0000". The bars' table marks the values the chart stars, every run of a tie, with the same hidden "(best)".

**The pairing** (`PairingPanel.tsx`), behind "Pair nodes…" — a button whose `aria-controls` names the panel only while the panel is open, since it is rendered only then: the stage section's subtitle counts the pairs drawn by hand that a run placed ("1 pair by hand", or "Paired automatically") — never one the API lists in `unplaced_pairs`, which a run of earlier content lacks the node of (decided in #402); those are listed in words under the stages, each with the run that lacks its node ("dense ↔ splade: not in run B", "…: not in the baseline"), drawn with the answer so nothing moves in later, the count message and the list inside a `role="status"` region ("Pairs drawn by hand not placed") that is always present, empty when every pair was placed — and then out of flow, so it adds no gap to the stages and moves nothing, while staying in the accessibility tree — so a list a re-compare brings or changes is announced; and a low-confidence row (the API's `confidence: low`) says the automatic pairing is a guess there. The panel pairs the baseline with one other run, as the API does: two columns of their retrievers, fusion and reranker, read from the stages; a link by dragging a node onto one of the other column, or by two clicks — either side first, Enter on a focused node being a click, Escape letting go of the picked one. Each change posts the **whole** pairing between the two pipelines through `POST /compare`, which keeps it, and the answer replaces the comparison. While it is in flight the panel is `aria-busy` and its status line says what is being kept; a second link made meanwhile is refused in that line, never dropped silently; once kept, the line says what was kept and how many pairs are drawn by hand ("dense paired with rrf; 1 pair by hand.", "Reset to automatic."). The list of pairs drawn by hand is always rendered, its height reserved, and holds the whole pairing kept: a pair the chosen run could not place is said so beside it, and stays in what a change posts, so drawing a pair never drops one an earlier run lacks; "Reset to automatic" posts no pairs, and a pair drawn by hand is removed alone. The links between the columns are drawn dashed for the automatic pairs — every node of a stage both runs have, since the API pairs by stage, not by node — and solid for the pairs drawn by hand. A run whose pipeline the API reports as `null` cannot be paired by hand, and the panel says why. A pair's optional label is not set from the panel.

**The verdict** is one sentence for **every** run against the baseline, composed by `verdict` on the histogram's metric where that run has it (else on `defaultMetric` of its own): counts, never adjectives — "131 queries improve, 108 are unchanged, 61 get worse — 6 by more than 0.3", the clause naming the most extreme worse bin that holds a query, by its bound. With no metric to read it from, the sentence says why: the two runs share no ranking metric when the ground truth is verified, or the ground truth's own detail when it is not. Each sentence is followed by its run's action: "Replay the N regressions", which opens the largest regression beside the baseline and keeps the set, `#replay/<run>/q/<query>?with=<baseline>&set=regressions&metric=<metric>` — the metric that run's sentence was composed on — so Replay steps through the others (§ The Replay screen); `regressions` in `model.ts` lists them from the API's worse bins, the lowest delta first. With no regression but some query changed, "Open <run> in Replay", `#replay/<run>`; and where no query changed at all (`hasChange`), no action, and a note that there is nothing to replay. The run the histogram shows holds the page's **one primary action**; every other run's action is secondary.

**At phone width** the screen fits the viewport, with no sideways page scroll (measured at 390 px in #428): the run bar and the controls wrap, the charts scale to the column, and **every table** — the metrics, the stages, the parameters, and each chart's table — scrolls sideways inside its own box, design/'s `Table` with `region`: a region named by the table's caption and a tab stop, so a keyboard can scroll it. A trade-off taken knowingly: each region is a tab stop and a landmark even when its table fits and nothing scrolls, since whether it overflows depends on the viewport and is not known when it is drawn. `.rg-compare` sets `min-width: 0`, because the shell's main column is a grid track its item sizes, and a chart's shown table does the same inside its chart's grid. In the pairing panel a node's stage is not written below the shell's 640 px breakpoint, so the node's name fits its column. Nothing moves at desktop widths.

**Keyboard and assistive technology.** Every chart's table is one button away, after its plot, and every table's scroll region is one tab stop. The histogram's bars are one tab stop; the run bar and the pairing panel are buttons and native selects. A change of runs is a change of view, so the shell moves focus to the screen's heading (§ The shell); a change of baseline is not.

## The Replay screen

`src/replay/` is the platform's differentiating view (ADR-016; the front-end design, § 3): one run's pipeline with what happened for one query on every node, and two runs stacked for the same query. It is the end of the third journey — Compare's histogram links each query to `#replay/<run>/q/<query>?with=<baseline>`.

**What it reads**, all through the generated client: `GET /runs/{id}` for the graph, `GET /runs/{id}/queries` for the query list, the per-run node metrics, the run's `ranking_node` and whether its ground truth is verified; `GET /runs` for the runs that can stand beside it, their names and the run's metric families; `GET /runs/{id}/trace/{query}` for the query; and, when the filter is on, `GET /runs/{id}/queries` with `missing_gold_at=10` as a declared query parameter. Side by side adds the second run's detail, queries and trace. Each read is keyed (`useRead` in `ReplayScreen.tsx`), only the answer to the last one asked lands, the request a new key, a retry or the screen going supersedes is cancelled through its signal — so thirty arrow presses through the list leave one trace request running, not thirty, and both the count and the cancelled signal drop its answer — and a newer query's trace is read while the one on screen stays, the stage `aria-busy` — the stage alone, so the status line and the list beside it still announce — and the status line, always present and its height reserved, saying "Reading query q2…". **Nothing is computed that the API computes** (the issue's Scope — OUT): metrics, per-query scores, gold ranks and each passage's grade are the API's, read from the trace (`runtime/ragondin-api/ARCHITECTURE.md` § Derived data). `model.ts` computes presentation only, each a pure function with its test: the shares of the query's time, the moves, the counterpart and the sentences. `fixtures.ts` is what the tests read: a hybrid with a reranker, a context builder and a generator; a dense-only run; the hybrid failing at its reranker; a run on another benchmark; a job that failed at its reranker, with the partial traces it kept.

**Over a job** (`#replay/job/<id>/q/<query>`), Replay reads a failed or cancelled run job's partial traces: `GET /jobs/{id}/queries` for the job, its graph and the queries it kept, and `GET /jobs/{id}/trace/{query}` for one, in the node shape a run's trace has — `fromPartial` in `model.ts` makes it the trace the stage and the inspector read (`ReplayTrace`), with no text, no scores and no passages check, since the API reads these traces against no dataset (`runtime/ragondin-api/ARCHITECTURE.md` § The partial traces, served). It is **labelled partial, never a stored run**: no run swatch or run name — "Partial traces" and the job's id in their place, the canvas named "Job <id>, partial traces, query <q>" — and a banner saying how the job ended, how many queries it executed, that no run was stored and why nothing is scored, with Open the job. Nothing stands beside it (side by side refused with its reason), the gold filter is refused ("Partial traces are not scored"), and the mode control reads "Alone"; no metric is offered. It opens on the query a failed job stopped on — the API's `failed_query`, whose trace ends in the failing node — else the first kept query, corrected in place. It reads no `/runs` path. A job without partial traces is the API's problem, shown as `ErrorState`.

**The address** is `#replay/<run>/q/<query>/node/<id>?with=<run>` (§ The router and the URL state), so a pasted link or a reload restores the run, the query, the node selected and the run beside. A node is named only after a query, since the stage draws nothing before one. The design and the issue wrote the side-by-side address `#replay/<run>+<other>/q/<query>`; the router already gave Replay `with`, and Compare links to it, so the screen keeps that contract rather than adding a second spelling. A query chosen, by click or by key, side by side turned on or off, and a node selected or the inspector closed are written in place (`{ replace: true }`): state within the view, so Back leaves Replay rather than stepping through queries, and focus stays where it is (§ The shell). The node stays selected, and in the address, as the query changes; which canvas it was selected on, A's or B's, is the screen's, since both select it where both have it. A node the rules below clear is taken out of the address in place. `#replay/<run>` opens on the first judged query in the list's order, corrected in place; a run with no query says so. **`#replay` alone is the run picker** (`RunPicker.tsx`, imported by the shell directly since it carries no canvas): `GET /runs`, each run in a native select by its name, short id, benchmark and prefix words, and "Replay this run" opening `#replay/<run>`; with no run, "No run to replay yet" and Open Runs.

**A set of regressions** (`&set=regressions&metric=<name>`, beside `with`): Replay asks `POST /compare` with the run beside as the baseline and the run — no pairing, so nothing is written — and takes the run's per-query deltas on that metric; which queries get worse, and their order, are `regressions` in `src/compare/model.ts`, Compare's own rule over the API's bins, never a second one. The list then holds the set alone, the largest drop first, under a line naming it with "Show all queries", which takes the set out of the address in place; the metric opens on the set's. Choosing another run beside, or one run, lets the set go, since it was read against the run beside. A failed read is `ErrorState` with Retry in the list's place. **Previous and Next** (`Steps`), above the list, move through what the list holds — the set, or every query — with where the query shown stands ("Regression 2 of 61", "Query 5 of 300"), each refused at its end; a query the list does not hold stands nowhere and Next opens the first.

**The toolbar**: the run's swatch, its name and its hash — a run's name, here and in "Beside", is the name its launch record gives, else the first current document holding its hash, else its short id (`runName`, ADR-C39 § 4's order); "Fork this run" (§ The editor), which opens the fork on the node selected; **"Open in the editor"**, a link to `#editor/<name>/node/<id>` on the node selected — so the selection survives the move from Replay to the editor — where `<name>` is a stored document holding what the run ran (`editorTarget` in `model.ts`): one of the listing's `pipeline_names`, the API's hash match, that the API reads (`refused_pipeline_names` left out), the name the launch record gives when it is among them, else the first. The launch record's name alone is never enough, since a document edited since the run is another pipeline and the node may not be in it. Without such a document the control is refused and says why — no document holds the run, the launched name has changed since, or the names that hold it differ from another only in case — and names "Fork this run", beside it, as the way to edit it; it is refused too while the runs are read, or when they could not be listed. Refused, it is a button, and open, a link: when the runs land and one replaces the other, focus held on it moves to the replacement rather than falling to the page. A node only run B has is no node of A's document, so both open the editor without it. **The way back** is the browser's Back: opening the editor is a move to another view, a new history entry, and the Replay address it leaves names the node; "One run" or "Side by side" (design/'s `SegmentedControl`), side by side refused with its reason when no other run shares the benchmark, or — a different reason — when the runs could not be listed; "Beside", the second run's chooser, offering **only the runs of the listing on the same `dataset_version`** — an address naming a run of another benchmark is refused in words and the one run replayed; a prefix run is named in it with `PrefixLabel`'s words, "prefix of <parent>, up to <node>", by its record or by structure (`prefixText` in `src/runs/model.ts`, Runs' own rule); and "Metric", the per-node metric, ndcg@10 by default, else the first metric the run's listing row calls a ranking metric in its `metric_families` (`defaultMetric` in `src/metrics.ts`, the one rule Pipeline and Compare's stage line and per-query metric open on; the browser keeps no copy of the catalogue to read a family from a name), else the first; local and unremembered.

**The query selector** (`QueryList.tsx`): a search over each query's text — the API serves it with the verified ground truth — and its id; the "No gold in the top 10" filter (design/'s `FilterChip`, its count once read, refused with its reason when the ground truth is not the run's); a count line; and the queries as **one listbox**, ordered by id with the numbers in it read as numbers (`byNumber` in `model.ts`: 1, 2, 10 — the API serves them by id as text), or in the set's order, one tab stop with `aria-activedescendant`, each option its id, its score on the chosen metric or "not judged", and its text. The arrow keys, Home, End, Page Up and Page Down move the choice and the address with it, stopping at the ends. **It is virtualised**: a box of fixed height, rows of a fixed 48 px, and only the rows in view plus a margin rendered, each with `aria-setsize` and `aria-posinset`, so SQuAD's ten thousand queries cost the DOM twenty rows; the current query is scrolled into view when a key moves it. design/'s `Table` is not used there: it renders every row.

**The canvas** is `src/canvas/`'s, in read mode, with the overlay `overlayOf` builds from the trace: per node that ran, its duration (a tenth of a millisecond below 10 ms) and its share of the sum of the trace's durations ("under 1%" for a sliver, never "0%"); the chosen metric for this query, to four decimals; the trace's `gold_ranks` as the rank strip's cells, for a node that produced a ranking; for any node fed chunks — a fusion, a reranker, a context builder alike — how many of them it did not keep; a failure with its message. A node of the graph absent from the trace — the nodes after one that failed — is "not run", and a failure is also said above the canvas ("This query failed at rerank; the nodes after it did not run."). A declared input carries no overlay. The overlay never reaches the layout (§ The canvas), so changing the query moves no node.

**The inspector** (`NodeInspector.tsx`), in design/'s `Inspector` shell: the node's meta line (duration and share, or the failure, or "not run"); its metric on this query and over the run ("0.8610 on this query; 0.7217 over 2 judged queries", from the listing's node metrics); what it produced, in rank order — its ranking, or a context's chunks in the builder's order — each item its rank, a ★ with "gold, grade 2" for assistive technology where the API's `grade` is above 0, its move against its upstream ("↑ 2", read "moved up from rank 2"; "↓", "new"), its chunk id in mono — and its document's beside it only when the chunk is a part of the document rather than the whole, so one id is never printed twice — and its passage text, clamped to three lines, with "Show all" (`aria-expanded`) where the drawn text overflows them; then what it discarded of its upstream, struck through with its former rank. **Upstream** is every node feeding it chunks, by port; a chunk's former rank is its best rank in any of them, so a fusion reads against the best leg. The context's text whole and the answer's text follow, and the query's text on the declared input. **The verdict** fills its slot when the selected node is its own run's final node (`terminalOf`: the node no edge leaves), and only once every run's query listing has loaded, since it reads each run's `ranking_node` there: one sentence composed by `verdict` from the query's score at the output and the gold ranks at the ranking node — "ndcg@10 is 0.8610 on this query, with 2 gold documents in the top 10, the first at document rank 1." — and side by side, both runs, their difference and both first gold ranks. The API's gold ranks count documents, chunks folded by first occurrence, where the list's ranks count chunks, so the sentence says "document rank". Before a node is selected the inspector's place holds one sentence, so selecting a node moves nothing. The query's text above the canvas takes two lines whatever its length — clamped, the whole text in its `title` and its accessible name — so choosing another query moves nothing below it.

**Side by side**: two canvases stacked, each under its run's swatch, both fitted to one frame — the larger of the two graphs' automatic layouts (`extentOf`, the canvas's `frame`) — so they share one zoom and line up from the same corner, rather than each fitting its own graph — the run replayed (A, below) in the first run ink, the run beside (B) in the second, the swatch carrying no letter (`RunSwatch`'s `unlettered`) and the run's name beside the colour — and the nodes a run has that the other lacks dashed with "only in <its name>" (the card's absent state, worn on the canvas where the node is drawn). **Replay names a run by its name, never a letter** — on the canvases, in the inspector, the verdict, the banners and the status line — so no letter crosses from Compare, where the same run may hold another (decided in #489); A and B in this section are the code's names for the two sides, never words on screen. Two runs of one name are each followed by their short id (`sideNames`). **B is drawn as current only on the query A shows.** Until B's answer for that very query has landed, **B's last canvas stays where it was** — the same canvas, never unmounted, so it does not flicker and keeps the reader's pan and zoom — muted, its accessible name ending "stale", and labelled over its frame — "Stale: query q1, reading q2…" while B's answer is being read, "Stale: query q1" once it is in and A's is not — so an older answer of B's is never passed off as one for A's newer query and the label moves nothing. Only the same run's canvas is kept, and only while B stays chosen: B put away or switched to another run forgets it, so B's first read — the same run chosen again included — holds B's place with a labelled loading line instead; and a failure of any of B's reads (its detail, its listing, its trace) is said in that place, `ErrorState` with Retry, never under a kept canvas. While B is not drawn as current, the inspector reads A alone and **leaves the verdict out**, since one run's verdict would stand where the two runs' belongs. Each run's passages are checked on their own, so B carries its own banner, opening on its name: "dense-only: passage text is hidden: …". **A selected node that neither graph on screen has is cleared**, rather than read as "not run" in A: but only once B is known, since the node is the address's and a reopened address must keep it: a node only B has goes when B is put away, when any of B's reads failed, and when B, switched to another run, is read and lacks it — while B is first read, or read again after a switch, it waits, said in the inspector as "No such node in <A's name>.", and is drawn in B once B lands; a node selected in B is cleared when B is put away in any case; and a node only B has, selected while B's kept canvas stands for this query, is said in the inspector as "No such node in <A's name>." Selecting a node on either canvas selects it on both where both have it, and the inspector, below the canvases across the stage's width, shows **two columns**, one per run: the node itself in the run it was selected in, and in the other its counterpart (`counterpart`) — the node of the same id, or, when there is none, "No such node in dense-only." and that run's final output, labelled "Final output of dense-only: dense". The final output is the last node of that run's trace: its terminal node, or the node it failed at.

**The passages banner**: when the trace's `passages` is anything but `verified`, design/'s `InlineMessage` names the case — the dataset is not on disk, differs, does not load, or its chunk set differs — with the API's detail, and the digests the run expects and those found on hover and in hidden text. The items then show ids: the screen shows only the text the API returned (ADR-C36 § 4).

**States**: loading is a sentence ("Reading run …", "Reading query q1…"), never a bare spinner; a failed read is `ErrorState` with Retry, in place of the stage for a trace (`query_not_found` included), so the toolbar and the query list stay usable; an empty run is design/'s `EmptyState`.

**Layout and assistive technology.** Three columns — the queries, the stage, the inspector — whose widths depend on neither the selection nor what is read; side by side, the inspector moves below the stage, by the mode, not by what has loaded. Below 1100 px they stack. At 640 px and narrower the list folds behind one control ("Queries · q12 of 300", `aria-expanded`), so the trace comes first; a query chosen with the pointer folds it again. Previous and Next stay above it. Inside each canvas's `application` role a node's figures reach the screen reader through its accessible description (§ The canvas); the inspector repeats them in text. A change of run is a change of view and moves focus to the heading; a change of query or of the run beside is not. **Not here**: editing, and Branch and Loop overlays.

## The Setup screen

`src/setup/` is where everything a run needs besides its pipeline is put in place (the front-end design, § 3 and § 6). Its subtitle says the one thing a reader of ADR-C32 § 2 would otherwise wonder: nothing on it enters a run's identity except the benchmarks' digests. It is one `Sheet` of four `Section`s, top to bottom — **Workspace**, **Benchmarks**, **Services**, **This build** — or, at the first launch, Workspace and the invitation.

**What it reads.** `GET /benchmarks` and `GET /services`, once each on mount and on its section's Retry, only the answer to the last read asked for landing; the page's job queue, for the downloads — it opens no stream of its own; the shell follows it and re-checks the build identity on each reconnection (§ The job stream); and the workspace the shell read (§ The shell), for the Workspace and This build sections and for the Connect form's families. Each section has its own loading, error and loaded state from `src/shell/states.tsx`: a failed read is that section's `ErrorState` with Retry, and the other sections render. A write's answer replaces the listing it returns rather than reading it again, and asks the shell to read the workspace again in place, so the counts and the top bar's service count follow.

**The first launch** (`FirstLaunch.tsx`, `isFirstLaunch` in `model.ts`): a workspace with **no benchmark on disk** — every entry `available`, which is the manifest's offer rather than something held, or none at all — **and no service bound**. The two lists are decided together, once both are read; while either is first read the page says so in one line, and a later Retry of one keeps the layout it has, so the page never collapses to the loading line. The invitation is two steps: *Add a benchmark* — the smallest `available` entry, read from the manifest's sizes and never named in the code, with its size, its licence and Download, then the import form — and *Connect a generator, if your pipeline ends in an answer*, with the sentence that a retrieval-only pipeline needs no service, composed from the retriever and reranker families this build carries locally (nothing is claimed when it carries none). The Workspace section stays above it. Importing a benchmark or binding a service ends it without a reload; an import moves focus to the Benchmarks section, since the form that had it is gone, and a connection moves it to the new row.

**Workspace**: the root, the datasets directory and the counts `GET /workspace` gives (runs, pipelines, benchmarks ready, services connected), and how to work in another workspace: start `ragondin ui --workspace <dir>` on its root. The screen has no workspace switch: neither the shell nor the API can change the workspace the binary serves.

**Benchmarks** (`Benchmarks.tsx`): design/'s `Table`, one row per registry entry in the listing's order — its name, its state as a `StatusChip` with the state's word (`ready`, `local`: done; `available`: queued; `differs`: warning; `unreadable`: failed), what the state means, its ground truth in words (`qrels`, `reference answers`, `qrels and reference answers`) and its licence, a link when the manifest gives where the terms are stated, before the action. `ready` is "verified" and its digest; `local` "imported, verified" and its digest; `available` its size, in decimal units; `differs` both digests and that the dataset on disk is not the one the manifest pins (or, for an import, the one recorded at import), with no Download; `unreadable` the adapter's error. A digest is shown short, the full value in its title. **Download** submits `POST /benchmarks/{name}/download` — the name one path segment, which the client percent-encodes (`beir%2Ffiqa`) — and the row follows the job on the job stream: its chip reads `queued`, `downloading` with a real meter, `verifying`, `failed` or `cancelled`, and its detail "Queued, 17.1 MB to download", then "Downloading… 6.8 MB of 17.1 MB" — the job's bytes, over its total, or over the manifest's size before the first tick gives one. When the job is done the listing is read again in place, so the row says `ready` and its digest, and the workspace is read again for its counts. **That read keeps the table**: if it fails, the table stays as it was, the row still says it is reading the digest, and the failure is an inline error below the table whose Retry reads it again — and, once that succeeds and the error goes with its button, moves focus to the section if it was left on the page's body. A write's answer that lands while it is in flight — an import — overtakes it, and it is sent again rather than dropped, since what it was for is not in the write's answer; a later read that overtakes it decides for it, so a later read that fails is no success, and the row keeps saying it is reading the digest. **While the job stream is down** — `disconnected`, never before its first connection — the section says "Job stream disconnected, retrying.", or, while a download is under way, "Job stream disconnected, retrying: progress shown is the last known.", on a line always present and as high as the longer sentence — one line, two at 640 px and below, where it wraps; a row whose job is under way adds "· last known" to its words — on the first launch, "· last known — disconnected, retrying" on the line beside Download — until the stream is back; it never reads as current while it is not. A refused submission is the API's detail, hint and code; a failed job is the registry's error, in the API's words; each is an alert, announced as it appears, and the button becomes **Retry**, which submits again. Progress is not a live region, so a tick every hundredth of the snapshot is not read aloud. **A download's faults are not shown here** — a choice made here: the only faults the queue reports beside a download are failed writes of its own record, which say what a restart will do with the job rather than anything about the benchmark, and the row goes back to the benchmark's own state once the job is done; the job's view at `#runs/job/<id>` lists them (§ The Runs screen). The control is **one button whose label changes** — Download, Downloading (refused, with its reason, while the job is under way), Retry — so focus stays on it; when the benchmark turns ready and the button goes with focus on it, focus moves to the section — judged again once the row is drawn, and only if focus is still on the page's body or that row's empty slot, so a person who moved on while the listing was read keeps their place. **Every row's action cell is one small control high** (`.rg-setup__action`), a button in it or not, so a button appearing, changing or going moves no row. Without a submission of its own, a row shows the benchmark's last download job in the queue — one started in another tab or before the page was opened, which the stream's first `resync` carries — except a done one, which the listing already says; a failed one there shows its failure and Retry. The first launch's Download is the same control, its words on the line beside it. There is no address field: a benchmark is a pinned snapshot (`docs/system-architecture.md` § 9.1). **Import a local corpus** posts a directory on the server's disk and a name to `POST /benchmarks/import`; a refusal is the API's detail and hint under the directory field, a success adds the `local` row the API answered.

**Services** (`Services.tsx`): one list item per binding, named by its `<family>/<name>` — the address in monospace, the status as a chip with its word last on its line, a line saying what identity was read and when, and a served model field, **Test** and **Remove**, each named for its row ("Test generator/qwen"). **A status** is decided by a probe this page ran at the binding's current address, when there is one: `connected`, `unreachable` (`service_unreachable`) or `refused` (any other probe refusal — `impl_not_in_build`, `binding_refused`, `request_invalid`, `service_not_found`); otherwise by the server's memory — `connected` when its last probe at this address read an identity — or `untested`. **The time** of a probe is this page's: the server keeps none, so a binding the server reports connected says its identity was "read before this page was opened", and the screen says so under the list. **A row's served model is this page's too**: kept per binding for the session, sent with each probe when given — an embedder, a reranker or a generator reports an identity only for one — and forgotten on reload. **The outcome** of a probe this page ran is said in the row's status line, a `role="status"` region always present — "Testing…", then "Connected · <identity>" — so a success is announced as well as a refusal, which is the row's inline `ErrorState`, never a toast; focus stays on Test. **Remove takes the row out of the list at once and writes nothing**: the message that offers Undo takes the row's place, as tall as the row was, so nothing below moves, and focus lands on Undo, which is described by that message alone. **The `DELETE` waits for the Undo window to close** (`UNDO_WINDOW_MS`, ten seconds), so Undo is a true undo: it writes nothing, and the binding keeps its place in `workspace.toml`, its comments and its row's place — a `DELETE` followed by a `PUT` would move the removed key's comments onto the next binding and append the binding at the end of `[services]` (`runtime/ragondin-api/ARCHITECTURE.md` § `workspace.toml`, read and edited in place). One window is open at a time: removing another binding writes the pending removal at once, and each removed binding keeps its own place, saying "Removed …" once written. When the window closes with focus on Undo, focus moves to the slot itself (a list item that takes focus by script), never to the page. **The `DELETE` removes by name, and the window lasts seconds**, long enough for another tab, the CLI or a hand edit of `workspace.toml` to bind the name again; so the screen reads `GET /services` first and deletes only if the name is still bound to the address that was removed. Bound elsewhere, nothing is written, the binding's row comes back at its new address, and the slot says it was not removed and why; no longer bound, the slot says removed and nothing is written. Binding the removed name again from the Connect form pauses the window while that `PUT` is in flight: a stored binding cancels the removal, a refused one opens the window again, so Undo still restores and the removal is still written when it closes. **One rule covers every other way a window ends: whatever would close it — another removal, leaving the screen, the page's `pagehide` — writes its removal at once, through the read before the `DELETE`, paused or not.** The read is what makes writing a paused removal safe: if the re-bind has already stored the name at its new address, nothing is deleted; if it has not, the removal is written, and a re-bind stored after it binds the name again. Leaving clears the window's timer with it, so nothing fires on a screen that is gone. Leaving the screen, or the page (`pagehide`), writes a pending removal rather than dropping it. A tab closed before those requests leave — the read, then the `DELETE` — keeps the binding: the safe side to fail on, and the binding is still listed when the screen is opened again. A refused `DELETE`, or a listing that cannot be read before it, brings the row back with the refusal below the list, and focus with it when focus was in the slot. ADR-C32's rule is under the list, in issue #345's words. **Connect** (`forms.tsx`): a family — a select over the families `GET /workspace` lists, a text field when none is known — a name, an address and a served model. The family sent is derived from the families known when it is sent — the one chosen if the list holds it, else the step's own default, else the first — since `GET /workspace` can answer after the form is drawn. It calls `PUT /services/{family}/{name}` and, once stored, the probe, then moves focus to the row; the row is drawn with the click as **pending** — a "connecting" chip, "Storing <family>/<name> in workspace.toml…" in its status line, Test and Remove refused with that reason, `aria-busy` — so the answers for a stored binding move nothing; a refused one takes that row away again, which moves the form below it, and focus moves to the address field that says why. A refused `PUT` is the API's detail and hint under the address field, and focus moves to that field so its description is read; a refused import does the same under the directory field. In a build without `remote` the form stays and says that a binding is stored and every test of it refused — the server's own `impl_not_in_build` then says why on the row. An empty list says that a pipeline runs only on the components this build carries until a service is bound.

**This build**: the version and the commit, read from `GET /workspace`'s `build` (`<version>+<commit>`, § The build identity handshake), whether it can call a `Remote` component, and design/'s `Table` of each family's `Local` implementations — "none in this build" where it has none — with the rule that adding one is a rebuild, not a setting.

**The address and focus.** `#setup/benchmarks` and `#setup/services` scroll to their section and focus it (`Section`'s `anchor`) once it is on the page — on load, and on every move between sections — while `#setup` focuses nothing. The sections come in tab order, top to bottom; every action is a native control, so Enter and Space work as they do anywhere.

**What it never does.** It opens no browser dialog — `prompt`, `confirm` and `alert` are unavailable in the viewer the design targets, and a test reads the screen's sources for any call to one — and no modal. It writes nothing the API did not answer, and makes every request through `src/api/`.

## The editor

`src/editor/` is the Editor screen: the canvas in write mode (§ The canvas) over one pipeline document, the palette beside it, the inspector for the selected node, undo and redo, and the server's verdict on the document as it stands (ADR-016 § 1: the same component as Replay's, in its second mode, with no second rendering of the graph). It **writes the document back as it changes** — continuous saving, no Save button (**Saving**, below) — and exports, imports and forks.

**The one-document rule.** The only in-memory shape of a pipeline the editor holds is the API's typed document (ADR-C40), `WireDocument` in `document.ts` — the generated `TypedDocument`, which has the shape of `RawPipeline` (`core/ragondin-pipeline/src/raw.rs`) as a configuration writes it: `pipeline: { inputs, nodes: [{ id, component, impl, inputs, params }] }`, a new one with no `version`, which reads as the version the server reads (INV-9) — and whose every parameter value states its kind, `{ kind, value }`: an integer as decimal text, a float as a finite number, text, a flag or a list. The browser never parses or writes the configuration format; the server renders it. Nothing lowered or logical is rebuilt in the browser. What the canvas draws, `toGraph`, is that document as the generated `Graph` — nodes sorted by id, one edge per input in port order, an input naming nothing drawing no edge — and is derived on every render, never stored. Positions are `EditorLayout`, beside the document, never in it (ADR-016 § 4).

**The store** (`store.ts`) is a reducer over the document and the layout with a history: add, connect, disconnect, set and remove a parameter, rename, delete, duplicate, move and arrange ("Tidy layout": every node where the canvas's automatic layout puts it, `resolveLayout` over the graph alone) are **one undo step each**, and a change that changes nothing is none; undo and redo walk the history, and any new change forgets the redo. A rename carries every input naming the node and its position with it, and refuses an id already taken. A delete removes the node and its position and **leaves its consumers naming it**: they are not rewired, `danglingInputs` marks each invalid in words, and the server's validation names the same as a dangling input. **Nothing rewires silently**: an id any node's inputs still name counts as taken (`freshId`), so a deleted node placed again takes a new id rather than its old edges back, and a rename to such an id is refused; and only the **last** edge into a node can be removed, since removing an earlier one would slide the later inputs into its port. Where the canvas's automatic layout put a node no position named is kept (`placed`) without being a step, in every state undo and redo reach, so neither moves it again. Selection is not in the store: it is the screen's, and the address's (below). A selection undo or redo takes away — a node placed, renamed or duplicated, then undone — is cleared, and the inspector draws the declared-input panel only for a declared input. A pending focus request (the node just placed, the inspector just opened) waits for its target to be drawn and expires once its target is gone.

**The verdict is never local** (`validation.ts`). After every change, debounced by `VALIDATE_DEBOUNCE_MS`, the typed document is sent to `POST /pipelines/validate` as `{ typed }` — which the server converts to the wire schema, renders as the configuration format and checks through its one load, so the hash it answers is the one of the bytes a write would store (ADR-C40 § 5) — and nothing else: no position (`validationRequest`). Its checks while editing — a taken id, a value its kind cannot carry, a port during the drag — only anticipate what the server says. The request a newer document supersedes is cancelled, and a verdict is shown only for the document it was asked about. The header shows the reply's canonical hash — the identity a run of this document would carry, which the editor never computes or caches (INV-8) — or `pipeline_invalid`'s words, or that the request itself failed; while a request is out it says "Checking with the server…", never "valid". The server's words land on the node its location names, as the card's invalid state, on the edge it names, dashed, and in the inspector — in its slot at the top and on the row of the port the edge enters. What is wrong is said once to assistive technology through a polite status region; a hash arriving is not announced.

**The port rules during a drag** (`ports.ts`) are structural, and kind rules only when a grammar is given. `refusal` refuses an edge into a declared input, an edge that would close a cycle (as such: "`a` feeding `b` would close a cycle: …"), a port that already holds an edge (naming what it holds), a port past the next free one — inputs are a list in port order — and a port a fixed family does not declare; and, given each family's ports, a kind the port does not take, naming the edge, then the kind expected, then the kind found, in the order `ragondin validate`'s report names them. **The kinds come from a `PortGrammar` handed in, never from a table here**: a table of each family's ports in TypeScript would be a second grammar. The screen builds it with `grammarOf` from `GET /workspace`'s capabilities, whose `ports` the server derives from `ragondin-pipeline`'s own `produced_kind` and `consumed_kinds`; a fixed family draws its declared ports, typed, filled or not, and a variadic one a port per input and one open after them. Handed no grammar (`null`), the canvas refuses no kind during the drag, draws one port per input and one open after them of no known kind (`opaque`), and leaves the verdict on kinds to the server after the drop.

**The palette** (`Palette.tsx`, `paletteOf`) is built from the capabilities and `GET /services`: one section per node family `GET /workspace` lists, in pipeline order (retriever, fusion, reranker, context builder, generator; the order is the only thing written here), each local implementation an entry, then each name Setup bound in that family marked Remote — refused, with the reason, in a build without the `remote` feature; a family with nothing says "None in this build."; then evaluation (the judge, M5) and control flow (Branch and Loop, M6), present and refused, saying which milestone brings them. `embedder`, which no node is, has no section, and there is no `Extension` entry. An entry is placed by a click, Enter or Space — beside the selected node, else right of the graph (or, on an empty canvas, where the automatic layout puts it), and in either case moved down the grid until it is clear of every card (`clearSpot` in `canvas/layout.ts`, the rule a stored layout's missing node follows) — or dragged onto the canvas, where it lands as dropped, and takes a fresh id derived from its `impl:` name (`bm25`, `bm25-2`, …). **A placed node is written with the starting value of each of its required keys** (`parameters.ts`'s `startingParams`), as the capabilities serve them for its family and name — a bound name takes its family's `bound` list, a carried one its own — and with nothing else: an optional key gets none, and a required key the composition root gives no starting value (a model, a path, an embedder, a served model) is left unset and marked, never filled with a placeholder. The values are ordinary values in the document, sent, hashed and stored as any other; the browser holds no table of its own. A refused entry stays focusable and says why on its second line. An implementation this build does not carry — the capabilities' `not_carried` — is listed in its family, refused, its second line the capabilities' reason ("Not in this build: needs the `onnx` feature.").

**The node menu** (`menus.tsx`'s `NodeEntries`, inside the canvas's menu shell, which follows the WAI-ARIA menu pattern): "Open parameters" (selects the node and moves focus into the inspector), "Duplicate" (a fresh id, its parameters and inputs, two grid steps away, selected), "Connect output to…" — **the drag's keyboard equivalent**: the menu becomes every input port of every other node, each open or refused with the reason the drag would show, and the entry itself becomes "Back to the node menu", keeping its element so focus stays on it — "Run up to this node" — its second line naming the nodes the prefix keeps and those it skips, and "no generation cost" when a generator is among them ("Keeps lexical, vectors, fused and reranked. Skips context and answer, so no generation cost."), a sentence since cost accounting is outside M4; choosing it opens Runs' launch panel cut at the node (`#runs?launch=<pipeline>&up_to=<node>`, § The Runs screen) — and "Delete node". It is refused, its second line saying why, on a node with no input yet ("This node has no input yet: connect one first."), on the pipeline's output as the server finds it (`terminal`: the one node no node reads, when there is exactly one — a stray node nothing reads leaves none, and the server cuts at either: "the prefix would be the whole pipeline"), on a context builder ("a context is scored by nothing"), on a pipeline not yet written, and while the canvas differs from what the editor last read or wrote — a change pending, a write out, a prompt up — since a run takes the document on disk (`runUpTo` in `prefix.ts`). These only anticipate `POST /runs`' refusals — the cut is the API's, on the wire schema — so the entry never offers a launch the server would refuse. Opened by right-click, the node's `more` control, Shift+F10 or the context-menu key. **A declared input has a menu too**, whose one entry is "Connect output to…", so the query is connected by keyboard like any node. "Delete node" is also Delete or Backspace on a focused node (a declared input is never deleted). After either, focus moves to a neighbour — what fed the node, else the first input — never to the page.

**The insert list** (`InsertMenu`): `/` with the canvas focused opens the palette's entries as a menu, refused ones saying why, focus on the first; the arrow keys, Home and End move, Enter or Space places and focuses the new node, Escape or Tab closes and gives focus back.

**The inspector in write mode** (`EditorInspector.tsx`), in design/'s `Inspector` shell: the server's words on this node in a slot of its own at the top, always there and of a fixed height, so a verdict arriving moves no field under the pointer — and, when the document validates and the server names nothing here, only a small "Valid" mark in it; every text the server or the editor writes with backticks (`` `x` is taken ``) is drawn with code spans, never its backticks (`src/words.tsx`'s `Words`, here and in the header, the cards, the canvas's status line, the menus, the palette, the prompts and the import); the node id, editable, committed on Enter or blur, a taken one — the id of a node or an input, or one an edge still names — refused here before the server would ("`x` is taken: a node, an input or an edge already names it."); its family and `impl:` name; its input ports, counted from one as "Input 1 (query): question", or "not connected" (the server's own words keep its port numbers), each with what feeds it, **only the last filled port carrying a control to remove its edge** (removing an earlier one would slide the later inputs into its port); and its parameters under ADR-C22's flat grammar, one field each **in key order** — the order the wire schema's map keeps them in, so nodes of one family read alike — **every parameter the implementation takes, set or not** (`parameters.ts`'s `parametersOf`: the capabilities' list for the node's family and name, with what its choice's key picks — a `dense` node's `embedder:` adding the ONNX keys or a bound embedder's `served_model`), each served one with what it is for on a line under its row, which its field names in `aria-describedby`; one not set is an empty field typed in its served kind, beside a line "Not set · <kind>" its field names too, that sets the key once a value is entered — a text key to the empty text on Enter in its empty field, never on leaving it — and refuses one its kind cannot carry, in words; **a required key the node does not set says "Required." as information**, never marked invalid before the person has done anything, and the node's card carries a neutral cue from the moment the node is there ("2 parameters to set", the canvas's `todos`: a plain wash, no alert glyph, no state, said in its accessible name too); **once the server refuses a save** (the save's `failed` phase, `check_keys` refusing the missing key), the field is marked invalid ("Required: the pipeline cannot be saved or run without it.") and the card's cue gives way to the invalid state ("`budget`, `separator` are required: set them in the inspector."), under a dangling input and the server's words — validation, structural, says nothing of it; a flag a checkbox, **each with its kind beside it** ("Kind of `k`": Integer, Float, Text, Flag or List, ADR-C40 § 8) — a key the implementation serves keeps its served kind, said and not offered for change, unless its value is written in another kind, when the picker offers that kind and the served one only — and a control to remove it; a value typed is committed once the typing rests `PARAM_DEBOUNCE_MS` (400 ms) when its kind carries it, and on Enter or blur otherwise, its refusal said only then, so a value half typed is never called wrong (a key not yet set waits for Enter or blur, since setting it redraws its row); **a commit while typing leaves the text as typed** — `1.` stays `1.` once 1.0 is committed, so the next digit makes 1.5, and a list ending in `, ` keeps its comma — and the field is redrawn in the value's own form (`1.0`) only when it is left, or when the value changes from outside, an undo for one; a refusal under a field scrolls that row, its error line included, into view inside the inspector's body, which keeps a scroll padding above the footer; then a new parameter's name, kind and value. **A value keeps its kind**: it is read back as its kind and refused in words when the kind cannot carry it — an integer is a whole number of at most 64 bits, held as decimal text so it is never rounded; a float is a number, **drawn with a fractional part** (`60.0`, `src/parameters.ts`'s `formatFloat`), and **a non-finite one** (`1e999`, `Infinity`, `NaN`) **is refused in words before it is sent**; a flag is `true` or `false`; a list is written as items separated by commas, each read as its first item's kind. **Picking another kind** reads the value as it stands in the kind picked — `60` becomes `60.0`, `60.0` becomes the text `60.0` — and is refused in words, the kind kept, when it cannot. A new value of no kind picked ("From the value") is an integer when it is a whole number, a float when it has a point or an exponent (`1.5`, `.5`, `1.`, `1e3`, signed or not), and **text otherwise — text holding a comma, and the text `true`, stay text** unless another kind is picked. No parameter carries a constraint hint beyond its kind, whether it is required and its description: the capabilities give no more. The inspector's verdict slot says, of a node the server names nothing about, whether a request is out, the document validates, the server stopped at a problem elsewhere (it names only the first), or the request failed. Its footer holds the secondary action **Run up to here**, the node menu's entry by another way: the same launch, refused with the same reason. **Its height is fixed** (96 px, scrolling inside), and **each port row keeps one line of fixed height** for its marker, empty or "The server names this edge." — the words themselves are in the slot — so a verdict landing moves no field.

**The keyboard.** Every pointer action has a key: placing (`/`, or Enter on a palette entry), moving (the arrow keys on a focused node), connecting ("Connect output to…"), deleting (Delete or Backspace on a focused node), the node menu (Shift+F10), undo (Ctrl+Z or ⌘Z) and redo (Ctrl+Shift+Z, ⌘⇧Z or Ctrl+Y) — heard inside the editor and with focus on the page itself, where it lands when what held it went away — and the Undo and Redo buttons in the bar, refused with the reason when there is nothing to undo or redo. Inside a text field Ctrl+Z is the field's own; on a checkbox or a button it is the editor's. **An edge is selected by a click** (write mode only): drawn heavier, said in the canvas's status line, with a "Remove" at its middle, drawn in graph coordinates inside the viewport so it follows a pan and a zoom — Delete removes it too, unless a node has the focus, which Delete removes instead; selecting a node, Escape or a click elsewhere lets it go — refused, saying why, for any but the last edge into a node, as the inspector's control is. Edges are no tab stops: the keyboard's way to remove one is the inspector's control. **Known limit**: the edge drag follows a mouse or a pen; on touch the release lands on the port the drag started from, so an edge is not dropped by finger — "Connect output to…" is the way there.

**The screen and the address** (`EditorScreen.tsx`). `#editor`, on a workspace with no pipeline file, opens on **the first-launch example** (below); otherwise it offers one action, "Start a new pipeline" — the editor over a new document holding one declared input, `query` — beside "Import a pipeline" and a link to Runs, and under them the workspace's pipelines to open: the recent ones as links, and every one in a picker, the recent first (`PipelinePicker.tsx`; `recent.ts` keeps the last five this browser opened in local storage, a per-viewer convenience). The editor's header carries the same picker, and **"Launch…"**, its primary action: Runs' launch panel on this pipeline (`#runs?launch=<pipeline>`), refused, saying why, as "Run up to this node" is, while the pipeline is not on disk or the canvas differs from it. The Pipeline screen's header and each Runs group header offer "Edit", into the editor. Whether the workspace is empty is the shell's `counts.pipelines` first, which costs no request, then `GET /pipelines`, which decides — the count is as old as the shell's last read — and gives the names a new document's first write must avoid. `#editor/<name>` reads `GET /pipelines/{name}` and its layout, `GET /pipelines/{name}/layout`, and **opens the stored pipeline on the canvas from the typed document it serves**, whether or not it validates (ADR-C40 § 4), at its stored positions: an invalid one opens with the server's words on it, as any edit's verdict lands. A layout that cannot be read opens the pipeline laid out by the canvas: positions are presentation, and never keep a pipeline closed. A document whose text does not read into the wire schema, or holds a value the typed document cannot carry (a non-finite float), comes with no typed document and is said to open as text only, in the server's words, with "Start a new pipeline" offered instead. The route `#editor/<name>/node/<id>` (§ The router and the URL state) carries the selected node — state within the pipeline's view, which moves no focus: it is restored when the address names it, and a node selected on the canvas is written into it, replacing the entry. Replay names its selected node in its address too, and opens the editor on it — "Open in the editor" over a stored document holding the run, or a fork — so the selection survives the move from Replay to the editor (§ The Replay screen). The editor offers no move to Replay: a document is not a run, and Replay needs one run and one query; Back returns to the Replay address that was left, its node with it. **One mounted editor is a session** (`EditorScreen`): the address moving to the file that editor has just written — a first creation, a save as a new file, or a rename — keeps it, its history and its selection; the address moving anywhere else, or "Discard my changes and reload", opens afresh from disk. So every change stays undoable across the write that names a file. Services read failing is an inline error with Retry in place of the editor.

**Saving** (`saving.ts`, the state machine; `persist.ts`, its requests). There is no Save button: after a change, once `VALIDATE_DEBOUNCE_MS` (250 ms) has passed and `POST /pipelines/validate` has called the document as it stands valid, `PUT /pipelines/{name}` writes it — the typed document, `{ typed }`, which the server renders with its one writer and stores (ADR-C40 § 5, ADR-C41) — with `If-Match` naming the etag of the last read or write. **An invalid document never reaches `PUT`**, and there is no "save anyway" (ADR-016 § 3). The debounce is the validation's: one rest of 250 ms after the last change, so git does not see every keystroke, and a write follows the validation of that very document, never a stale one. The states: **dirty** (the canvas differs from what was last read or written) → **validating** → **valid-unsaved** → **saving** → **saved** | **conflict** | **hand-written-pending**, and **failed** for a write the server refuses otherwise (the composition root's key refusals), not retried until the document changes. A write in flight or a choice awaited holds every other write back; the newest valid document is written once it is answered. The file line under the bar, a polite live region, says which: "Saved" — only once this editor has written the file; a file just opened says "No changes since it was opened" — "Saving…", "Unsaved changes", "Unsaved — N errors" (the nodes the canvas marks invalid, at least one), or what saving waits on; the verdict line beside it shows the canonical hash the server answered, which is the hash `ragondin validate` prints for the bytes written (INV-8). **The browser never holds a copy of a file it did not read from the API**: what is on disk, as far as the editor knows, is the last document it read or wrote, and nothing is cached between sessions. **Leaving the editor flushes it** — another address, another pipeline, "Discard my changes and reload", anything that unmounts it: the last document is validated if the server has not yet called it valid, and written over the etag held once the write in flight has answered (a newer document queued behind that write included); the last positions are written at once. Nothing held behind the stale-etag or the hand-written prompt is written, and nothing after a stale etag; a document never written is created under the name its question offers, never over another file, rather than lost. While anything is not on disk — a change, a write out, a prompt up — closing or reloading the page asks the browser to confirm (`beforeunload`), since a page being torn down cannot be trusted to finish a request. *A leaf choice, recorded here*: the debounce is the validation's 250 ms, with the flush on leaving and the browser's confirmation as its two ends; there is no write on a field's blur.

**The two prompts** (`SavePrompt.tsx`), inline messages under the bar, never a modal: the canvas stays usable behind them and nothing is written until one of their actions is taken. **A stale etag** — `412 precondition_failed`, the file changed on disk since it was read — stops saving and offers "Discard my changes and reload", which says first that the canvas's unsaved changes are lost, or "Save as a new file" under a name the person gives, created with `If-None-Match: *`; never a silent overwrite, never a silent discard. **A hand-written file** — `GET /pipelines/{name}`'s `canonical` is false: its text is not the server's own rendering of the document it reads to — is not rewritten until its first save has asked, once: the rewrite replaces the text with the server's rendering and drops what that rendering does not keep, **named in full** (ADR-C40 § 7, `DROPPED`) one click away, under "What a rewrite drops": its comments, its formatting, its key order, expanded references (an anchor and its aliases written out at each use), and keys the pipeline schema does not read; the message itself is two sentences, and its two choices sit side by side in one row: "Rewrite this file", or "Save as a new file", which leaves the original's bytes untouched. The choice to rewrite is remembered for that file for the browser session (`session.ts`, session storage; unavailable storage asks again, never writes unasked). This is the application's second confirmation dialog, after deleting a workspace, and there is no third. A new name already taken, or refused, goes back to the prompt with the server's reason. **A new file is written only from a document the server called valid**, as every write is: while it is not, "Save as a new file" is refused, saying so. Each prompt says that **changes made while it is open stay on the canvas and are not written until the person chooses** — never dropped silently.

**The layout** is written to `PUT /pipelines/{name}/layout` on every position change a step makes, debounced by `LAYOUT_DEBOUNCE_MS` (250 ms) — a drag or a run of arrow keys is one write — with no gate, since a layout is never invalid and never hashed (ADR-016 § 4). Where the canvas placed nodes itself on opening is kept and written with the next change, never on opening, so opening a file writes nothing. It is written only once the document is on disk, since a layout needs its pipeline, and **never while a prompt is up or a save as a new file is out**: the positions then go beside whichever file is chosen — what was last written is remembered with the file it was written beside, so a save as a new file writes them again there. The layout is written with no `If-Match`: it has no etag of its own (last writer wins, `runtime/ragondin-api/ARCHITECTURE.md` § The pipelines).

**Export**, from the bar: the server's rendering of the document as it stands — `POST /pipelines/validate`'s `rendering`, the bytes a write of it stores — offered as read-only text (selected whole when focused) to copy and as `<name>.yaml` to save; refused, saying why, while the document does not validate. Nothing of the browser's own is added.

**Import** (`Import.tsx`), from `#editor`'s empty state: a YAML document pasted or chosen from disk is sent to `POST /pipelines/validate` **as text** — checked as `ragondin validate` checks a file (ADR-C40 § 6) — its refusal shown with its node and edge when the server names them; on success it is written **byte for byte**, `{ document }` with `If-None-Match: *`, under the name the person gives (a chosen file proposes its stem, and the name follows each file chosen until it is typed), and the editor opens on it. The file chooser is drawn as one of the design's buttons beside the chosen file's name; the document box is monospace; why "Validate and import" waits is said beside it; and a refusal is said once — the server's "the pipeline does not validate:" prefix is dropped under a title that says so. Its comments are kept, so its first save from the canvas asks first.

**Fork from a run** (`Fork.tsx`'s `ForkButton`, in Runs' bar and Replay's toolbar): "Fork this run" reads the run through `GET /runs/{id}`, writes its `configuration` — the document `bench` kept, verbatim — byte for byte as a new pipeline file named `<launched name>-fork`, or `run-<id>-fork` for a run with no launch record, the first such name free, created with `If-None-Match: *` — a name taken between the listing and the write is skipped for the next one free, never replaced; copies the layout copied at the run's launch, `GET /runs/{id}/layout` (copied by `POST /runs` from the pipeline's layout, a prefix run's from its parent's), beside it when there is one (else the canvas lays the fork out); and opens the editor on it — from Replay, on the node selected there, which the fork has since it is the run's own configuration. A layout that could not be copied is said in words, with a link to open the fork, which the canvas then lays out. The editor's file line names the run it was forked from, remembered for the browser session (`session.ts`). One click from Runs once a run is selected: the iterate journey is Runs → Fork → one parameter → Launch → Compare.

**The first-launch example** (`example.ts`): on a workspace with no pipeline file, the editor opens on a retrieval-only pipeline built from the capabilities, never a stored fixture — the lexical leg, `bm25` on the query, placed as the palette places it, with the starting values the capabilities serve — which runs without any service and without any file beyond the benchmark (the design document § 3). A dense leg is left to the palette, even in a build that embeds locally: it needs a model and a tokenizer on disk, which a new workspace does not hold, so it would fail at launch. A build without `bm25` opens on the empty document, its palette saying why. **No file exists until the first edit or "Keep this pipeline"**, and then **its name is asked first** (the saving state's `naming` phase, an inline question under the bar like the two prompts, which confirms nothing): "Name this pipeline to save it.", the field pre-filled with `example` (or the first `example-N` free) — `pipeline` for a new one — or with a name typed in the title before, and written under the name given, created with `If-None-Match: *`; a name taken, or refused, asks again with the server's reason. **The title renames**: "Rename" turns it into a field, Enter renames and Escape keeps the name. Before the first write it only changes the name the question offers; after, it calls `POST /pipelines/{name}/rename` over the etag held (`runtime/ragondin-api/ARCHITECTURE.md` § The pipelines), which moves the file, its layout and its pairings — the bytes, so the etag, unchanged — and the editor writes on under the new name, the address following it in the same session; what the browser session remembers of the file (the rewrite chosen, the run it was forked from) and the recent list follow it. While the rename is out nothing is written, neither the document nor the positions, so no write lands under the name it moves away from. A refusal — the name taken (`pipeline_exists`), files a removed pipeline left under the name (`request_invalid`), the file changed on disk, a write in flight — is said under the field. A rename the server did but could not finish — the layout left under the old name, an old pairing not removed — is taken as done, and its `fault` said in the header.

**Layout and assistive technology.** A bar — the name and its Rename, the picker, Launch…, the history, Tidy layout, Export, the verdict in a line of fixed height that scrolls — the canonical hash drawn as its first twelve characters, the whole in its title, copied whole by a click — so a long report is never cut off, and under them the file line, at least one line high — then the prompt saving waits on and the export, when there is one, each the full width; then the palette beside the canvas; below 900 px they stack. Nothing on the screen changes size with what the server says: the verdict line, the inspector's verdict slot and its port rows keep their heights, and the canvas's status line floats over the graph — below the toolbar and wrapping at 640 px and narrower, so its reason is never cut off.

## The canvas

`src/canvas/` is the pipeline canvas: **one component**, `Canvas`, for every screen that draws a graph — Replay, the editor, Compare's mini-shapes (ADR-016, its first decision: read mode and write mode are the same component). It is built on React Flow (ADR-C36 § 5) and the automatic layout on dagre (`DEPENDENCIES.md`). `src/canvas/index.ts` is its public surface.

**The contract.** `Canvas` takes the lowered graph as `GET /runs/{id}` serves it — the generated `Graph` type, never a hand-written one — and, all optional: a stored layout (the generated `Layout`'s `nodes`, node id → position), a per-node overlay, the selected node (controlled, or kept by the canvas when left out) with `onSelect`, `onAutoPlaced`, an `inspector` slot drawn beside the canvas while a node is selected, and the node menu's entries, each handed a way to close the menu once it has acted. `mode` is `'read'` — pan, zoom, select and open the menu, nothing that changes the graph — or `'write'`, which adds what the editor needs (§ The editor) and removes nothing: nodes move, by drag (snapped to the 16 px grid) and by the arrow keys (a grid step, four with Shift), each move handed to `onMove`; an edge is drawn from an output port onto an input port and handed to `onConnect`; `/` asks for the caller's insert list (`onInsert`); a palette entry dropped on the canvas is handed to `onDropItem` with where it landed; `ports` gives each node the ports it draws, so an empty slot shows; `issues` draws a node in the invalid state with the validation's words, and `invalidEdges` an edge dashed; Delete or Backspace on a focused node is handed to `onDelete`, whatever edge is selected; a click selects an edge, whose "Remove" — or Delete — is handed to `onRemoveEdge` unless `refuseRemoveEdge` says why not. What may move is keyed on `mode` through one table in `Canvas.tsx`; every write-mode prop is read in write mode only, so Replay and Compare pass none and see nothing change.

**Edges in write mode are the canvas's own drag, not the library's.** The library's connection mechanism stays off in both modes (handles never connectable as either end): a pointer down on an output port starts a drawing, and from then on every input port asks the caller's `refuse` whether it would take the edge, and wears the answer — `data-drop="open"`, a halo, or `data-drop="refused"`, a strike through its mark, so the refusal is a shape and not a colour alone, its reason the port's title. The status line beside the toolbar, `role="status"`, says the reason of the port under the pointer, or how to finish; it is always on the page and floats over the graph, so nothing moves when it speaks; at 640 px and narrower it sits below the toolbar and wraps. A release on an open port calls `onConnect`; on a refused port, anywhere else, or Escape, nothing is made. The canvas judges nothing itself: `refuse` is the editor's. The keyboard's way to draw an edge is the editor's "Connect output to…" entry of the node menu (§ The editor); a node's `more` control, at the card's corner and shown on hover and focus, opens the same menu by pointer and is no tab stop, since Shift+F10 is the keyboard's. A click inside the node menu stops there, so it neither selects the node nor closes the menu: the entry decides. The library's stylesheet takes pointer events from a handle it cannot connect, so `Canvas.css` hands them back to the ports in write mode.

**The nodes are controlled through `onNodesChange`** in both modes: a drag's positions and each card's measured size come back as changes and are kept — a size not handed back on its node is forgotten the next time the nodes are handed over, and a fit would then frame only the cards measured since — and any other change, such as a fit asking for the nodes again, is answered with fresh nodes, which is what lets the library run a queued fit. In read mode a caller may pass `frame`: the view is then fitted, through the library's `fitBounds`, to the graph's box grown to the frame from its top-left card (`fitArea` in `layout.ts`), once the pane has a size and again when the pane or the frame changes — never as the overlay changes — and the toolbar's fit does the same; two canvases of one size given one frame share a zoom and an origin. In write mode the view is fitted again, at once and never above 100%, whenever a node comes or goes and whenever the pane resizes (the inspector opening beside it), so a node just placed is on screen.

**Loading.** The canvas and its two libraries come to about 82 kB gzipped. Replay imports it, and loads as a lazy route chunk (`React.lazy` over an `import()` of the screen, in `src/shell/screens.tsx`), so the shell and the other screens do not pay for it; the editor does the same, `src/editor/EditorScreen.tsx` loading `Editor.tsx` lazily, so its empty state costs nothing.

**What it never knows.** It makes **no request** — everything arrives through props, so ADR-012 holds by construction, and the network lint (§ The network lint) covers it like any module. It knows no screen: no route, no query selector, no run. It never computes or shows a hash, and a layout is presentation only (ADR-016, its fourth decision; INV-8): the canvas is whole with no layout at all.

**The model** (`model.ts`). `toModel` turns the graph into cards: the declared inputs as query nodes; each node's family mapped to the design system's by design/'s `familyOfComponent`, the one definition Runs uses too (`context_builder` → context), and any family the design system has no card for — an extension node, Branch or Loop — to the neutral diamond tile (`docs/OPEN_QUESTIONS.md` § 7 stays open); the implementation line spelled `<family>/<impl>` as the configuration writes it, and `pipeline input` for an input; the one key parameter per family the design system shows (`top_k` for retrievers and rerankers, `k` for fusion, `budget` for the context builder, `temperature` for the generator), drawn with its kind (`src/parameters.ts`: `60.0` for a float, never `60`), and nothing when the node does not set it; one input port per edge in port order, typed by the edge's kind, and the output typed by the first edge leaving the node or else by the family. The nodes come out in **topological order**, ties broken by the canonical order (inputs, then node id) — the order Tab walks.

**The layout** (`layout.ts`) reads **the graph and the stored positions, nothing else**. With no stored layout, dagre places the graph left to right — ranks `--space-16` apart, two grid steps between cards of a rank, every card snapped to the 16 px grid — and `layout.test.ts` holds the constants equal to the tokens. Every card takes **one height envelope**, the tallest a card gets (the head, the replay body's four rows and a failure message), whatever it shows: the overlay never reaches the layout, so the query on screen in Replay never moves a node, and what `onAutoPlaced` reports does not depend on it. With a stored layout, each named node is drawn where it says, and dagre does not run when the layout names them all; a node it misses is placed by dagre and moved down the grid until it is clear of every placed card. Either way the nodes the canvas placed itself are handed to `onAutoPlaced` once per distinct placement, so the caller can persist them, and the legend says so: "Laid out automatically", or how many nodes it placed (the front-end design, § 6). The legend names each port shape with the word "port" after it ("query port", "candidates port"), so the query port is never read as the query family beside it. `clearSpot` is the same move-down rule for one card asked for at a spot, which the editor places a node by.

**The node card** (`NodeCard.tsx`, `Port.tsx`). The design system's NodeCard, transposed as the primitives were (§ The design system): family tile with glyph, name, implementation, key parameter, and every state as a prop drawn from a data attribute — selected, keyboard focus, invalid and failed with the message inside the card, running with counted progress, queued, dragging, the ghost drop target (drawn, inert, hidden from assistive technology), not in this build, replay, the dashed "absent from the other run" state with its tag in words, and "not run" — an earlier node failed for this query — drawn dotted, never dashed, so it does not read as absent, with the word in its head and no result rows. **Ports are typed by shape**: a circle for the query, a square for candidates (`chunks`), a diamond for context, a leaf for the answer, and for `opaque` a ring around a dot, hollow whether connected or in replay so it never reads as the query's filled circle. A port is filled where an edge meets it — every input, and the output when an edge leaves the node. The fills live in `Port.css` and `NodeCard.css` alone: `Canvas.css` hands the library's handle its surface through the library's own variable and declares no port fill, so no rule loaded after them competes. `Port.test.tsx` reads the computed style of all five kinds, unconnected, connected and in replay, on the card alone and on a real `Canvas` with its stylesheet (`GATED_GEN`), and fails if two kinds draw the same mark or the opaque ring fills. The card knows no canvas library: the canvas passes `renderPort` to draw each port as a library handle, and the preview draws plain marks. It lives here rather than in `design/` because it is the canvas's card: the design system's issue left it out on purpose, and the canvas is its only consumer.

**The overlay** (`NodeOverlay`): per node, the duration and the share of the query's time (a bar proportional to the share, never under 2 % so a sliver shows), the metric text, the gold ranks (the design system's ten-cell `RankStrip`: it takes ranks, not scores), the discarded count, an error (the failed state), `notRun` (the not-run state) and `onlyHere` (the dashed absent state). Each field draws on its own; an overlay, even empty, puts the card in replay, and none at all draws the plain card. In replay the ports go solid and smaller, **and keep their shape**: a deliberate departure from the design system's reference, which draws every replay port as the same small dot. The reference's dots would make the five kinds one mark in exactly the view where a reader traces what flowed where, against the rule that ports are typed by shape and colour never carries a meaning alone.

**Keyboard and selection.** Tab reaches the toolbar first, then the nodes — the only tab stops inside the graph; edges are not focusable — in topological order. Enter selects the focused node, a click selects, Escape clears; one node at a time. In write mode the arrow keys move the focused node and `/` asks for the insert list. Shift+F10, the context-menu key or a right-click opens the node menu shell on that node and focus moves to its first entry; the arrow keys, Home and End move between entries; Escape or Tab closes it — the menu handles both, so Escape there leaves the selection alone — and gives focus back to the node, and focus leaving it closes it; it closes once. Its entries are the caller's, and with none it says there is nothing to do here. Each node is named for assistive technology by family, name and implementation, then "selected", "failed" or its absent tag, and described by the keys that work: "Enter selects, Shift+F10 opens the menu, Escape clears.", and in write mode "Enter selects, Shift+F10 opens the menu, the arrow keys move it, Delete removes it, Escape clears." — set through the library's `ariaLabelConfig`, whose default names Space and Delete as the library binds them, which the canvas does not: it binds Delete itself, in write mode only. A node the validation named adds "invalid" to its name. The zoom percentage is shown, not announced.

**The `application` role.** The library puts `role="application"` on its graph element, after the props it passes through, so it cannot be changed without patching the library. It is kept, and is right for read mode as well: the graph is a composite widget with its own keys — Enter, Shift+F10, Escape — which a screen reader's browse mode would otherwise take for itself. The canvas names it with its `label`; the toolbar and the legend sit outside it, read as ordinary content, the toolbar named "Canvas, " and the canvas's `label`, so two canvases side by side are told apart. The SVGs the library draws and takes no attribute for are set from a `MutationObserver`: each dot grid `aria-hidden`, and the `<svg>` wrapping each edge `role="none"`, which leaves the named edge inside it exposed where hiding the wrapper would hide it too. One consequence follows: inside the application a screen reader hears a node's name and its description, not the text of the card. So **a replayed node is described by its figures**: `describeOverlay` (`model.ts`) says what the card draws — "Failed: …" or "Not run.", the metric, the rank strip's sentence (design/'s `rankSentence`, the strip's own words), the discarded count, the duration and the share — and the canvas renders it in a hidden element per node, which the node's `aria-describedby` names before the keys' description (set through the library's `domAttributes`, which it spreads after its own). A node with no overlay is described by the keys alone. Its name stays family, name, implementation, then "selected", "failed", "not run" or its absent tag. Each `Canvas` owns its React Flow provider, its flow id and its selection, so two side by side share nothing.

**Motion.** Only selection and focus animate, through the duration tokens that reduced motion collapses (§ The design system); the library's edge animation and animated viewport moves are not used.

**The library stays behind the wrapper.** An ESLint `no-restricted-imports` rule refuses `@xyflow/*`, `@dagrejs/*` and `d3-*` anywhere outside `src/canvas/`, the library's stylesheet included, so a change of wrapper touches no screen; and it refuses `zustand`, the library's internal store, **everywhere**, `src/canvas/` included, because importing it would be the UI taking on a state store, which escalates (`AGENTS.md` § Conventions). `tests/canvas-confinement.test.ts` checks both against the real configuration. Like the network lint it is a scan of import declarations, and it does not see a dynamic `import()` of a package, a re-export (`export * from '@xyflow/react'` from a module of `src/canvas/` would hand the library to anyone importing that module), or a CSS `@import` of the library's stylesheet. Review covers those.

Inside, three things are set on purpose: the library's `base.css` is the only stylesheet of its own taken (positioning; no theme), and everything visible is restyled with tokens in `Canvas.css`; each node is given its size envelope and its handles' positions before it is measured, so edges are drawn from the first frame and in a DOM with no layout; and **the library's attribution stays visible**, bottom right, restyled with tokens — decided by the product owner on #348. The library's MIT licence asks only that its copyright notice be kept, but the library's stated policy is that the attribution link stays unless the user holds a React Flow Pro subscription, removal being a permission of that subscription (the attribution's own markup says so: hide it only when subscribed to React Flow Pro). This project holds none, so the link stays.

## The end-to-end journeys

`e2e/` holds the M4 exit criterion's journeys (the front-end design, § 2 and § 3), run by `npm run e2e` against the real binary: **first run** (`first-run.spec.ts`: an empty workspace, Setup's two-step invitation, the fixture corpus imported and verified, the editor's first-launch example kept, launched from Runs, the run filed), **iterate** (`iterate.spec.ts`: Runs → "Fork this run" → the dense leg's `top_k` from three to one → launch → Compare against the original), **investigate** (`investigate.spec.ts`: Compare → the histogram's regressed bin → a query in Replay side by side → the node only B has, selected, and what each run produced there), **keyboard only** (`keyboard.spec.ts`: from Runs, two runs selected, Compare, Replay, a node selected on the canvas and its menu opened, by Tab, the arrow keys, Space, Enter, Shift+F10 and Escape alone), **the two launch records** of decision #390 (`launch-records.spec.ts`: Runs and the Pipeline screen over the run without a record and the run whose recorded name's content has since changed), **the Pipeline screen's Run buttons** (`pipeline-launch.spec.ts`: three subsets of the fixture corpus's queries imported through the API, each a column of its own, "Run on <benchmark>" into Runs' launch panel with that benchmark chosen and the cell filled once the run is filed, then "Launch the N missing runs": the panel lists every missing benchmark, says why the manifest's two — not on disk, a download away — are not launched, and one confirmation launches a run per remaining column), and **the accessibility pass** (`accessibility.spec.ts`). A reader of a test recognises the journey by its name and its comments, which follow the design's words.

- **The real binary, one per test, over a workspace of its own.** `e2e/support/fixture.ts` copies the fixture workspace — or makes an empty directory, for the first run — starts `ragondin ui --port 0` from it, since the documents' model paths are relative to the workspace, reads the address from the line the binary prints, and kills it after the test. Nothing is shared, so a journey that launches a run changes no other test's workspace, and the tests run in parallel. `just test-ui-e2e` builds both inputs and names them: `RAGONDIN_E2E_BINARY`, the binary, and `RAGONDIN_E2E_FIXTURE`, the directory `just fixture-workspace` writes — `workspace/`, `corpus/` and `fixture.json`, which names each run, so no test spells a run id.
- **The fixture workspace is the Rust tests' own**: `bin/ragondin/tests/support/workspace.rs` builds it from the exit criterion's fixtures — the corpus imported as `beir/exit-criterion`, `dense-only`, `hybrid-rerank` and `bm25-only` with their layouts, four runs — and `bin/ragondin/tests/fixture_workspace.rs` checks it as the API lists it before the journeys read it as the screens draw it. One truth on both sides (the front-end design, § 9).
- **No network.** Every request the page makes to another origin than the binary's is aborted and recorded, and a test that made one fails (`oneOrigin`): the one-address rule, held in a browser. Importing the fixture corpus stands in for "obtain SciFact", whose download needs the network; that path is exercised by the ignored `bin/ragondin/tests/journey_scifact.rs` alone.
- **A journey's last address reproduces its view.** `e2e/support/views.ts` opens the address a journey ended on in a fresh browser context — no history, no storage — and asserts the same heading and the same accessibility tree of what the journey names as its view: the runs table, the comparison, the inspector.
- **The accessibility pass** runs `accessibility-checker-engine`'s WCAG 2.2 A and AA rule set on each of the six screens, at an address that shows it with content, in the light and the dark theme chosen with the theme control; AA is the level the design system holds its contrast to (§ The design system). The engine is injected as an init script, since the content security policy refuses an inline one; the check waits for every finite transition to end first, since a colour read mid-transition is not one the page settles on; and only definite violations fail it, since "needs review" is a judgment. **Any violation fails it**, listed by screen, rule and the engine's message, every element attached to the result; the check waits on no animation that never ends, and gives up on a page that does not settle within five seconds. On each screen it first asserts the theme chosen is still the page's. Then, with `prefers-reduced-motion` emulated, no animation or transition on any screen lasts longer than 1 ms: the design system collapses every duration to 1 ms rather than to none, so a transition still ends and fires its events (`design/base.css`).
- **The fixture leaves the final metrics alone in iterate**, by construction: the cross-encoder recovers every query whatever one leg's `top_k` (`bin/ragondin/tests/exit_criterion.rs` says why the fixture was built so), so the delta the journey asserts is where the change acts — the ranking after fusion in Compare's stage line, and the parameter in its configuration table.
- **The dev server's fixture mode.** `npm run dev:fixture` (`just ui-dev-fixture`) starts the same binary over the fixture workspace and runs Vite with `RAGONDIN_API` naming it; `vite.config.ts` then forwards `/api` to it (`scripts/dev-proxy.mjs`), with the `Host` and the `Origin` rewritten to the binary's own, since it answers only the authority it printed and refuses a state-changing request from another origin (`runtime/ragondin-api/ARCHITECTURE.md`). The page still reaches one origin, the dev server's. Without `RAGONDIN_API` there is no proxy, as before. `tests/dev-proxy.test.ts` pins the entry and refuses an address that is not loopback `http`.
- **Types and lint.** `tsconfig.e2e.json` checks `e2e/` and `playwright.config.ts` under `tsc -b`, with the DOM's types for the functions a test runs inside the page and Node's for the rest; the lint reads them with Node's globals. The network rule applies to them as to everything outside `src/api/`, and they name no network primitive: the page's requests are the page's own.

## Toolchain

The choices ADR-C36 § 5 left to the implementation, and why each was made:

- **Node 24**, the current LTS major, pinned once in `.node-version`. CI's setup action reads that file; `engines` mirrors it and `.npmrc`'s `engine-strict` makes `npm ci` refuse another major. `tests/node-version.test.ts` fails when the two name different majors.
- **Vite 7, not 8.** Vite 8 depends unconditionally on `lightningcss`, licensed MPL-2.0 — which `deny.toml` leaves off its list deliberately, as file-level copyleft. Moving to Vite 8 is therefore a change to the licence policy of both toolchains, taken in `deny.toml` first, not a version bump.
- **No React plugin.** esbuild compiles JSX with the automatic runtime by itself (`vite.config.ts`). The plugin's contribution is Fast Refresh in the dev server; without it an edit reloads the page. The plugin's line for Vite 7 (5.x) also pulls `@babel/core`, and through it `caniuse-lite`, licensed CC-BY-4.0, off the list.
- **happy-dom, not jsdom**, as the test DOM. jsdom's tree carries MIT-0 and CC0-1.0 packages, off the list, and its current release declares `engines` of Node `^24.15.0`, a minor the major pin does not guarantee; happy-dom is MIT with a small tree.
- **TypeScript 6.0.** TypeScript 7 exists, but `typescript-eslint` supports up to 6.0; the lint parses with the same compiler the type check runs.
- **Vitest and Testing Library** for tests, **ESLint** with `typescript-eslint` for the lint, as the front-end design names them.
- **The end-to-end runner** is the one the front-end design names, `@playwright/test`, driving Chromium, the one browser CI installs. Apache-2.0 throughout; its browser is downloaded by its own command, outside the lockfile and outside the audit, as the ONNX Runtime archive is outside `check-deny` (ADR-C27).
- **`accessibility-checker-engine`, not `axe-core`**, for the accessibility pass: the front-end design names axe, whose licence, MPL-2.0, `deny.toml` leaves off the allow list deliberately (as file-level copyleft, the reason Vite stays at 7, above). The engine chosen is Apache-2.0 with no dependency, and ships a WCAG 2.2 A and AA rule set.

## How the assets reach the binary

`npm run build` writes `dist/`, which is ignored by the repository: nothing here commits built assets. `bin/ragondin`, built with its `ui` feature, embeds `dist/` as it was at compile time, and `ragondin-api` serves it at `/`, answering every path whose last segment names no file with `index.html` so the UI routes itself (`runtime/ragondin-api/ARCHITECTURE.md` § The assets); when `dist/` is absent it embeds a page saying the UI was not built and how to build it, so `cargo build --all-features` never needs Node (ADR-C36 § 5). Build the UI before the binary, then, for a binary that carries it. The build writes the third-party notices into `dist/` with the rest (§ The third-party notices), so the binary serves them at `/third-party-notices.txt`. CI's `ui` job does exactly that after `npm run check`, and its test step fails if the binary embedded the notice page or serves no notices (`bin/ragondin/ARCHITECTURE.md` § The ui subcommand says how).

Everything the binary serves, `index.html` included, is under the content security policy `default-src 'self'` (§ The one-address rule): an inline `<script>` or `<style>` in the built page would be refused by the browser. Vite's default output carries neither.

## The design system

`design/` is the design system as code, and the only place a colour, a type style, a space, a radius, a shadow or a duration is written. Issues cite `ui/design/` the way a Rust issue cites an ADR, and a change to it is reviewed that way: it is the reference every screen is checked against, not an implementation detail of one. Where the design system's source and a later need disagree, the change lands here first, with its test.

**Tokens are the only source of colour, type and spacing.** A component names a role — `var(--ink-2)`, `var(--surface)`, `var(--type-dense)`, `var(--space-3)` — never a value, and takes every colour from the token set of the surface behind it: a chip on a `surface` uses the inks and washes defined for surfaces, and the same markup under a dark subtree reads the dark values without a line changing. Tokens are named by role (`--ink-2`, not a grey step), so a theme swaps values and touches no component.

**How tokens flow into CSS.** `design/tokens.json` is the token source, carried over from the design system with the usage note of each token. `scripts/tokens.mjs` renders it into `design/tokens.css`, which is committed; `npm run tokens` regenerates it, and `tests/design-tokens.test.ts` fails when the committed file is not what tokens.json renders to, so neither can drift from the other. The same test pins the node-family pigments, the run inks and the better/worse, state and accent pairs to the design system's values in both themes. It also computes, in every theme block, the WCAG contrast of each family's on-ink (`--on-family-<family>`, the ink a tile's glyph and a latency-stack segment's name are drawn in) against that family's pigment, and fails below 4.5:1: a node's name is 11 px text on its pigment. One ink cannot clear that on every pigment of a theme — in dark, fusion, context, judge and query take the dark ink, retriever, reranker and generator the light one — so each family has its own. The four dark-ink tiles therefore look darker than the other three in the dark theme; that is by design, and folding them back onto one ink puts their names under 4.5:1 again. The dark retriever pigment is set to clear 4.5:1 with a margin (4.64:1), so that an 8-bit rounding step in either direction still leaves it above. `base.css` imports `tokens.css` and `fonts.css`; `src/main.tsx` imports `base.css` once; each component imports its own stylesheet, and Vite bundles them all into the one CSS file the binary serves. Tokens that do not change with the theme — the three font families and their fallback stacks, the twelve type styles as `font` shorthands (with a `-tracking` companion), the 4 px spacing grid, radii, control and canvas sizes, durations and easings — sit in one bare `:root` block. Under `prefers-reduced-motion` every duration but `--duration-0` becomes 1 ms in `tokens.css`, and `base.css` catches any literal animation.

**The theme mechanism.** Every colour and every shadow is themed; the generator writes them three times:

- the complete light palette on `:root, [data-theme="light"]`, with `color-scheme: light` — so every token has a value on bare `:root` before any block redefines it;
- the dark palette under `@media (prefers-color-scheme: dark)`, on `:root:not([data-theme="light"])`, with `color-scheme: dark` — the system's choice, unless the page has chosen light;
- the dark palette again on `:root[data-theme="dark"], [data-theme="dark"]`, with `color-scheme: dark` — the page's choice, or a subtree's.

The test asserts that both dark blocks redefine exactly the set the light block defines. A theme applies to any element carrying `data-theme`, not only the root, which is how the preview shows both themes side by side and how a theme switch will set one; `base.css` gives every `[data-theme]` element the `--ground` background and `--ink` colour, so a themed subtree repaints its own ground and its bare text rather than inheriting the other theme's ink. A token whose role differs by theme is its own token rather than a dark-only selector, so the `prefers-color-scheme` path gets it too: `--seg-thumb` is `surface` in light and `line-strong` in dark, so the segmented thumb reads as raised above its track in both. An alias (`--focus-ring: var(--accent)`) is written in every themed block rather than once, because a custom property's `var()` resolves on the element that declares it: declared once on the root, a dark subtree would inherit the light accent.

**Styling: plain CSS, no CSS-in-JS and no component kit** (ADR-C36 § 5). Class names are global and carry the `rg-` prefix, which is their scope. A state or a variant is drawn from the element's ARIA attribute or a `data-*` attribute — `aria-pressed`, `aria-checked`, `aria-selected`, `aria-current`, `aria-invalid`, `aria-busy`, `aria-disabled`, `data-state`, `data-tone`, `data-cell`, `data-best`, `data-connected`, `data-floating`, `data-error` — never from a class, so the rule that draws a state and the attribute assistive technology reads are the same fact, and a test finds one by the other. The one attribute no product markup sets is `data-preview-state` (`hover`, `focus`, `pressed`), listed beside the pseudo-class it mirrors so the preview page can show a hover, a focus ring or a press at rest. CSS Modules were not used: the tests assert the rule that draws each state by its selector, and the selectors keep the design system's own vocabulary, so a reviewer compares a component with its reference one to one. `.rg-visually-hidden` lives in `base.css`: a component that carries its second channel as hidden text needs the base stylesheet loaded.

**Colour is never the only carrier.** A status, a family, a run or a better/worse reading always comes with a glyph, a letter, a mark or a word: `StatusChip` has its icon or meter and its word, `RunSwatch` its letter (or "baseline" and a dashed outline) — or, `unlettered`, the run's name beside it, where a screen names runs by name alone (Replay) — `Delta` its sign, arrow and a hidden "better" or "worse", `FilterChip` a check when pressed, `RankStrip` filled versus hollow cells and a sentence, `TopBar` and `StatusDot` a hollow ring and "unreachable", `InlineMessage` a glyph named "Error", "Warning" or "Note", the best table value its weight and a hidden "(best)". Each such component's test asserts the second carrier, not only the colour.

**Components.** One directory each under `design/components/`: the component, its stylesheet, and a test per state that asserts the rendered state and, where the state is drawn by CSS (hover, pressed, focus), the rule that draws it — the test reads the stylesheet with Vite's `?raw` import, which is why `vite.config.ts` sets `css: true`. The API is small: props for state, children for content. `InlineMessage` is a live region of its own — an alert when critical, a status when a warning — unless `live={false}`, for a message inside a live region its caller keeps mounted, so a change is announced once, by that region; its glyph still names its tone. `Progress` throws without a finite value: there is no indeterminate variant; its `progressbar` role sits on the track, named by the count, so an action beside the count stays a button. A disabled `Button` is `aria-disabled` rather than natively disabled: it stays in the tab order and its reason describes it — the one accessible path, beside any description the caller gave, with no `title` repeating it — so a keyboard or screen-reader user reaches the reason without a pointer. Because `aria-disabled` stops nothing by itself, a disabled button is forced to `type="button"`, so it submits no form by click, Enter or Space, and none of the caller's activation handlers — click, double click, auxiliary click, context menu, key down, up and press, pointer, mouse and touch press and release, submit, in either phase — is passed to it; its focus and hover handlers are, because a tooltip saying why it refuses is wired through them and is needed most while it refuses. A busy button is forced to `type="button"` too, so it does not submit twice. A disabled `FilterChip` or `Checkbox` shows its reason as visible text that describes the control rather than joining its name. A row's `bestColumn` is one column or, on a tie, several: the API's best is every run holding it. The selected `Table` row carries `aria-current`, which a table row honours, and a bar on its edge beside the tint. `Table` gives each group its own `tbody` under a `th scope="rowgroup"`, whose label is any content — a name, or a link with tiles and a count. With `rowHeaders`, each row's first cell is its `th scope="row"`, kept in view at the left edge while the table scrolls sideways, the corner header above both sticky edges, so a cell is announced with its row as well as its column: a matrix rather than a list; a `span` row is two cells, its label and one sentence spanning every column after it, with or without `rowHeaders` (without, the label is a data cell). Every sticky header sticks within the table's own scroll box, which is its scroll container: the column headers stay in view while the box scrolls, not while the page does. The box is positioned, so a cell's visually hidden text — absolutely positioned — is clipped by it rather than widening the page from a far column. With `region`, the scroll box is a region named by the caption and a tab stop, so a keyboard scrolls a table wider than the screen with the arrow keys. Given `onOpen` or `onToggle`, its rows take the keyboard as **one tab stop** (`design/roving.ts`): the up and down arrows — stopping at the first and last rows, not wrapping — Home and End move focus and the stop between rows, Enter opens a row and Space toggles it without scrolling the page; a row is named by its `label`, a `passive` row (a placeholder) takes no focus, a key pressed on a control inside a row stays that control's, and focus entering a row by a click makes it the stop. The ring sits inside the row, so the table's scroll box does not clip it. A `Select` is described by its help line and by any `aria-describedby` the caller gives, both, so a note beside the field reaches assistive technology without displacing the help. A `Checkbox` takes an `accessibleLabel` when its visible label alone does not say which item it selects, and a `tabIndex` of -1 inside such a row, which takes its keys while a click still toggles it. `SegmentedControl` and `Tabs` keep one tab stop — on the first option when the value matches none — and the arrow keys move the choice without scrolling the page. `Section` takes an `anchor`, a ref that makes it a place an address can move to: it takes focus by script (`tabIndex` -1, never by Tab) and is announced as its region. `RunSwatch` takes a `copyLabel` ("run A") naming which run its hash button copies, where several sit side by side; the button's name carries the six characters it shows ("Copy 9e2b7d, the hash of run A"), so a person who says what they see reaches it (WCAG 2.5.3). `TopBar`'s workspace slot takes any content — a path, or the shell's workspace indicator, which is a link to Setup (§ The shell) — and its `status` slot shows the application's own status, such as its event stream, as a live pill with its dot and its word. `StatusDot` is the dot every such status draws: filled when something answers, a hollow ring when it does not, always beside a word. `ButtonLink` is a real link drawn as the button of its kind and size, for a move to another view; an action that changes something stays a `Button`. `PrefixLabel` is a prefix run's label wherever one is shown — Runs' rows, Pipeline's runs, the launch panel — "prefix of <parent>, up to <node>" in caption ink beside the `prefix` glyph, the words carrying the relation and the glyph hidden from assistive technology; `prefixWords` gives the same words to a `<select>` option, which holds text only: two parents both named, more as the first and a count, so the label stays one short phrase. `FamilyTile` (a family's pigment with its glyph) is a primitive beside `Glyph`, because the inspector's head and the canvas both need it; beside it, `familyOfComponent` says which tile a node takes from its family as a configuration and the API spell it (`context_builder` is `context`), or none for an extension node, whose kind is open — the one mapping every screen that draws a graph uses. Two choices differ from the design system's reference markup, and why: `SegmentedControl` is a `radiogroup` of `radio`s rather than pressed buttons, since one tab stop moved by the arrow keys is the radio-group pattern assistive technology expects; `StatusChip` has a `warning` state beside the four the issue named, because the design system draws one, and a `cancelled` state — a close mark in the neutral ink, a stop someone chose rather than a failure — because the job queue's rows need one.

**Charts** live in `design/charts/`, added with the Compare screen, the first to need them: hand-written SVG, and HTML for the histogram, with no charting dependency. They are generic — they know runs as `RunSeries` (an id, a label, the letter written beside the mark and its slot's ink) and node families as `Family`, never a comparison — and the screen composes them. `ChartFrame` is every chart's figure — its SVG plots are hidden from assistive technology, while the histogram's bars, being buttons, stay live: its caption names it, its legend is required (it throws on an empty one, since every hue on screen is data a legend explains), and a button below the plot shows the same data as a table, the caller's, which is the chart's equivalent for assistive technology — or, where that table is already on the page below the chart (`tableBelow`), a line names it instead, so no second copy hides behind a button — an SVG plot itself is `aria-hidden`, and so is `ChartTooltip`, the hover box, which repeats what the table holds. `BarChart` draws grouped bars, `LineChart` one line per run across ordered positions, `StackedBarChart` horizontal stacks, each on **one linear scale** (`scale.ts`: `linear`, round `ticks`, and the `PLOT` box every chart is laid out in, in SVG units; the plot is drawn at most that wide in CSS pixels, so a label keeps its type size and is never magnified, and narrower on a narrow screen, where it scales down). Their hover targets are the whole band a group, a position or a bar sits in, larger than any mark. A run's mark is told by its `data-ink` and the letter written beside it — under each bar, at a line's last point, letters ending at one position spread evenly about their points, both ways, so none hides another — and the baseline is a dashed neutral outline or line; a missing value draws nothing, never a zero, and a line breaks at it: a segment joins only neighbours both present, and the hover layer says why the value is missing in the caller's words. `StackedBarChart` takes family pigments by `data-family` and no run ink, with a surface-coloured hairline between neighbours; a family with no pigment is drawn neutral, and colour is never what alone tells two of its segments apart: a segment wide enough for its node's name is labelled with it, a narrower one with its family's glyph, a narrower one still with nothing beyond the hover box and the table. A segment that took any time is drawn at least 2 SVG units wide, so a family the legend names always has a mark — a fusion of microseconds beside a reranker of seconds included; the segments after it follow it rather than cover it, so a bar may end that much past its scale per such segment, and the total written at its end is the true one. Whether a name fits is decided from a per-character upper bound on its width in `--type-micro`, set at or above the advances of the shipped face, never by measuring laid-out text, so nothing moves once the font arrives; each label sits in a nested `<svg>` the size of its segment, which clips it there, so no label reaches a neighbour's. Labels are written in their family's own `--on-family-<family>` (a segment drawn in the neutral pigment takes `--on-family-query`), the ink made for content on that pigment. `Histogram` is a group of buttons, one per bin, each the height of its column, named by its content (its bin and what its two numbers are in visually hidden words ("much worse, 6 queries, change below −0.3"), its count and its range as shown, so the words on screen are words of its name: WCAG 2.5.3), one tab stop moved by the arrow keys, Home and End, `aria-controls` on every bin, naming the list an open bin fills, which is always on the page, and `aria-expanded` true on the bin whose contents are open, drawn with an accent outline and underline rather than a wash; its arms take the reserved `--worse` and `--better`, its middle `--delta-zero`, and its halves are written in words with an arrow. Text is always in an ink token. Each chart's test renders it under both `data-theme`s and checks the token its marks read against the theme's block of `tokens.css` (`design/testing/themes.ts`).

**Fonts** are the upstream projects' own woff2 files, unmodified, in the upright weights the type scale uses (`design/fonts/LICENSES.md` lists them, where they came from and why each weight is there). `fonts.css` points every face at `./fonts/`, never at a host, with `font-display: swap` so the fallback stack stands in while a face loads. The wordmark's 650 resolves to the 700 file by the browser's weight matching.

**Glyphs** are one SVG file each under `design/glyphs/`, drawn on a 16 px grid in `currentColor`; the files are the source. `Glyph` inlines a drawing by name, read from the files at build time with `import.meta.glob`, so it takes the ink of its context and nothing is fetched. `GLYPH_NAMES` and the directory are held equal by a test.

**One origin** (§ The one-address rule): `tests/design-assets.test.ts` reads every stylesheet, component, SVG, HTML entry and `tokens.json` under `design/` and `src/` and fails on any `scheme://` address, whatever its host (a name, an IP, `localhost`), and any protocol-relative `//host` opening a string or a `url()` — an SVG's `xmlns` namespace aside, which nothing fetches. The design system's reference stylesheet loaded its faces from a font host; that line has no counterpart here.

**The preview page**, `design/preview/`, renders every primitive in every state, in both themes side by side. It is the reviewer's tool: `npm run dev`, then `/design/preview/`. It is not an input of the production build, whose only entry is `index.html`: `tests/design-preview.test.ts` runs the same build `npm run build` runs into a scratch directory, lists what it wrote and fails on any preview file or any file carrying the preview's markup; it also starts the dev server and fetches the page.
